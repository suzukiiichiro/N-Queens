## 388: `-d`デバッグフラグ + rev番号ディレクトリへのログ集約

**位置づけ**: 今週月曜にご依頼いただいた項目2「-dオプションでデバッグ
出力、ncuなどを含む実行ログ一式がrev番号ディレクトリに出力される」への
対応。ncu自体は別スクリプト(N=21固定)のまま、というのは既にこの
セッション序盤で確認済みの方針。

**Python側(`388Py_kernel_maxd14_final.py`)の変更、最小限に絞った**:

- `-d`を位置に依存しない独立フラグとして実装。`sys.argv`をそのまま
  使わず、`-d`トークンを取り除いたローカルコピー`argv`を作り、
  それ以降の全ての位置引数解析(21箇所)は無変更のまま`argv`を参照する
  形にした。`sys.argv`自体は一度も再代入していない(Codonのネイティブ
  `sys`モジュールが再代入可能かどうか不明だったため、安全側に倒した)。
  これにより`-g -d`・`-d -g`・`-g 21 21 32 484 1 0 7 37 -d`のいずれも
  同じ意味になる。
- `-d`の効果は`gpu_log_level`を(既存の値がより高くない限り)1以上に
  引き上げるだけ。ディレクトリ作成・ログファイル書き出し・ncu実行は
  このCodonバイナリからは一切行わない。

**bash側(`388_debug_run.sh`、新規・日常使い用)**:

- `{REV_TAG}_debug_{タイムスタンプ}/`ディレクトリを作成し、
  ビルドログ・実行ログを`tee`で書き出す。既存の全`*_validate.sh`が
  使っているのと同じパターンで、新しい仕組みは何も発明していない。
- 引数を省略すると`-g -d`を実行、渡された引数に`-d`が無ければ
  自動的に末尾へ付加する。
- ncuは実行しない(375以来の方針通り、N=21固定の別スクリプトのまま)。

**次の小さな一歩(未着手)**: ncu専用スクリプトが同じディレクトリへ
書き込むようにする統合は、今回は見送った。まとめてやるより、この
ncu専用スクリプト自体を新規に作る(または既存の375由来のものを
再利用する)タイミングで、出力先だけ`388_debug_run.sh`が作った
ディレクトリに合わせる形が良いと思う。

**事前予測**: `-d`をどこに置いても(先頭・末尾どちらでも)N=6の
`total=4`という結果自体は変わらない、と予測する。`-d`ありの時のみ
`[debug-mode] enabled via -d: gpu_log_level=1 ...`のバナー行が出て、
`-d`なしでは出ない、と予測する。

## 【r2訂正】記録出力とログの分離

387実行時の実機出力をご覧いただいたところ、`[crunner-dispatch-summary]`
や`[crunner-input-missing]`が`-d`の有無に関わらず常にコンソールへ出て
いることをご指摘いただいた。調べたところ、`bench_mode==37`自体の状態
表示5箇所(`crunner_run()`内の`[crunner-dispatch]`・
`[crunner-dispatch-done]`、`main()`内の`[crunner-unsupported]`・
`[crunner-input-missing]`・`[crunner-dispatch-summary]`)は、385以来
`gpu_log_level`に関係なく無条件にコンソールへ出力されていた。r1で
`-d`を導入した際もここは見落としていた。

**r2の修正**:

- `rev386_validation_helpers.py`に`crunner_dispatch_log(log_dir, line,
  gpu_log_level)`を新設。常に`{log_dir}/dispatch.log`へ追記し、
  `gpu_log_level>=1`(`-d`で引き上げられる)の時だけ追加でコンソールにも
  出す。
- 上記5箇所すべてをこのヘルパー経由に変更。
- **表の行(N/Total/Unique/time、記録出力そのもの)は無変更のprint()の
  まま、常に表示される**——ここが今回の分離の核心で、鈴木さんの
  「記録出力以外のログはログディレクトリへ」というご指摘にそのまま
  対応する。
- ついでに、旧リビジョン番号が残ったままだった`385_crunner_logs`
  ディレクトリ名を`crunner_logs`(特定リビジョンに紐づかない永続的な
  実行時データという性質に合わせた)へ改名した。

**これで**: `-g`単独(計測時)はコンソールに記録出力の表だけが並び、
`crunner_logs/dispatch.log`に詳細が残る。`-d`を付ける(デバッグ時)と
同じ詳細がコンソールにも出る。

**事前予測**: N=21を`-d`無しで実行すると、コンソールには
`21: 314666222712 ... ok`の行だけが出て`[crunner-*]`系の行は一切出ない、
しかし`crunner_logs/dispatch.log`には`[crunner-dispatch-summary]`
一式が残る、と予測する。

**結果(r2)**: 2026-09-07、cudacodon実機で`bash 388_validate.sh`実行、
`OK=14 FAIL=0`で`388 PASSED`。

- N=6の`-d`位置非依存性テスト(先頭・末尾)、両方OK。
- **核心チェック**: N=21を`-d`無しで実行したところ、コンソール出力は
  ```
  GPU mode selected
   N:             Total           Unique         hh:mm:ss.ms
  21:      314666222712                0          0:03:23.228    ok
  ```
  のみ。`[crunner-dispatch]`・`[crunner-dispatch-done]`・
  `[crunner-dispatch-summary]`など`[crunner-*]`系の診断行は一切コンソール
  に出なかった(`console_clean_without_-d`)。
- それでいて`crunner_logs/dispatch.log`には`[crunner-dispatch-summary]`
  一式がきちんと記録されていた(`dispatch_log_file_contains_summary`)。

**確定**: 記録出力とログの分離は実機で意図通りに機能した。計測時
(`-g`単独)はコンソールに表だけが並び、詳細は`crunner_logs/dispatch.log`
に残る。デバッグ時(`-d`)は同じ詳細がコンソールにも出る。

## 【r4】CRunnerバイナリ自体にも同じ問題があった

r3の直後、鈴木さんから「.cuファイルは内容が同じだとしても、過去のRevを
流用するのではなく明示的に同一Rev番号を振ってRev毎に完結した管理に
したい」というご指摘をいただいた。`crunner_dispatch_table()`が指す
バイナリが`./364_kernel_maxd14`のままだった——ディレクトリ名(r3)と
根が同じ問題が、参照するバイナリ名にも残っていた。

**r4の修正**:

- `388_kernel_maxd14.cu`を新設。`364_kernel_maxd14.cu`の**純粋な
  リネーム**。ヘッダーコメント内のビルド/実行例5箇所
  (`364_kernel_maxd14` → `388_kernel_maxd14`)を更新し、リネームの
  理由を説明する段落を追加しただけ。**`#include`以降のコード領域
  (カーネル本体・ホストランナー)はdiffで完全一致を確認済み**
  (sha256: `b51735b2cf3ec2ed084849dc3ed7eafc1cb6e5c808169c519cf03f2f64d6622d`、
  リネーム前後で同一)。
- `crunner_dispatch_table()`のバイナリパスを`./364_kernel_maxd14`から
  `./388_kernel_maxd14`へ更新。
- `388_validate.sh`側も、このバイナリが未ビルドの場合は`nvcc`で
  ビルドする処理を追加(これまでの385〜388検証は既存の`364_kernel_
  maxd14`バイナリの存在を前提にしていたが、今回は新しいファイル名
  なので実機で一度もビルドされていない)。

**まだ実機未確認**: コード自体は364由来で何度も実機確認済みだが、
**この新しいファイル名でのnvccビルド自体はまだ実機で行っていない**。
論理的には同一コードなので同じ結果になるはずだが、確認するまでは
「確認済み」と言わない、というこのプロジェクトの原則通り、次の実機
実行で確定させる。

**結果(r4)**: 2026-09-07、cudacodon実機で`bash 388_validate.sh`実行、
`OK=16 FAIL=0`で`388 PASSED`。

- `388_kernel_maxd14.cu`の`nvcc -arch=sm_86`ビルドが、この新しい
  ファイル名で実機初めて成功(`crunner_binary_present[388_kernel_
  maxd14]`)。
- N=21(`bench_mode=37`、`-d`無し): `total=314666222712`(オラクル
  完全一致)、`0:03:23.239`——364由来のビルド(385/386/387で確認した
  `0:03:23.2xx`台)と実質的に同一の実行時間。
- コンソールは記録出力の表のみ、`388_crunner_logs/dispatch.log`に
  詳細が記録されていることも確認。

**確定**: コード領域がbyte-identicalであるという静的な確認(sha256
一致)が、実機でのビルド・実行結果によっても裏付けられた。以後
`crunner_dispatch_table()`は`./388_kernel_maxd14`を正式に参照する。
