## 393-2. 新規実測1 — `long_scoreboard`の99.77%が単一命令に集中

| addr | samples | 内訳 | 命令 |
|---|---:|---|---|
| `28a980` | 82,010(**全体の6.20%、単独2位**) | long_sb 73,616 / wait 3,239 | `LOP3.LUT R16, R5, c[0x0][0x1b0], RZ, 0xc0` |

カーネル全体の`long_sb`は73,784。**そのうち73,616(99.77%)がこの
1命令**である。355/357はこの5%台を分解していなかったが、実体は完全に
局在していた。前後を見れば正体は明白である:

```
28a920  IMAD.U32 R2, R8, 0x8, R1
28a930  LDL.64 R4, [R2+-0x8]      ← pop(R4,R5)
28a940  LDL.64 R10, [R2+-0x10]    ← pop(R10,R11)
28a950  IADD3 R8, R8, -0x2, RZ    ┐
28a960  IMAD.MOV.U32 R9, RZ, RZ, RZ │ 独立命令わずか3個
28a970  IADD3 R0, R0, -0x1, RZ    ┘
28a980  LOP3.LUT R16, R5, mask    ← LDL.64の結果を待つ
28a990  SHF.R.U32.HI R5, RZ, 0x1b, R5
```

`.cu`側のフレーム定義と一致する:

```c
stack[sp+1] = col | ((avail | (depth << 27)) << 32);
```

popした上位ワードから`avail`(maskでAND)と`depth`(>>27)を取り出す
2命令のうち、前者がロードレイテンシを丸ごと受けている。

## 393-7. Codon版とC版はSASSレベルで別物である

stage 3が出力したC版のSASSと、stage 1のCodon版を比較した。

| | Codon版 | C版(389) | 差 |
|---|---:|---:|---:|
| SASS命令数 | 664 | **472** | **-28.9%** |
| `BRA` | 68 | **37** | -45.6% |
| `LOP3` | 150 | **83** | -44.7% |
| `BREAK` | 13 | 7 | -46.2% |
| `BSSY`/`BSYNC` | 18 / 18 | 17 / 17 | -5.6% |
| ローカルメモリ命令 | `STL.64`×4 / `LDL.64`×2 | **`STL.128`×2 / `LDL.128`×1** | 幅2倍・本数半分 |

**Codon版はフレーム(16バイト)を`STL.64`×2 / `LDL.64`×2で出し入れし、
C版は`STL.128` / `LDL.128`各1本で済ませている。** 393-2で特定した
`28a980`の直前がまさにこの箇所である。

スケジューラサイクルあたりのスレッド命令発行数:

- Codon: 0.32 × 7.17 = **2.29**
- C: 0.28 × 10.13 = **2.84**(+23.6%)

373が確定した「新環境ではCodonがCより約13.6%遅い」と符号・桁が整合する。
**注意**: stage 2は並べ替え済みchunk0(743,424件)、stage 3はフル
2,025,282件の1launch目であり、処理タスク集合が異なる。厳密な統制比較
ではなく、傾向の一致として扱う。

**この一致が意味すること**: C版は命令あたりのストールはむしろ悪い
(5.33 > 4.82、`branch_resolving` 24.2% > 20.4%)にもかかわらず速い。
勝因は**レーンの少ない領域の命令数を減らしたこと**であり、それが
`Avg. Active Threads / Warp` 10.13 vs 7.17 という形で現れている。

### 記録の訂正(私の見積もりの誤り)

393の一次解析で私は「命令数削減・スケジューリング改善という軸は上限
一桁%であり、N=21を3:23→2:02にする目標には届かない。届きうるのは
warp intrinsicsによるレーン発散対策だけだ」と述べた。**これは誤りで
あり撤回する。** 誤りの内容は、*Codon版のサンプル分布から読める局所
寄与率*を、*その軸の変更で得られる利得の上限*と取り違えたことである。
実際には、命令数削減という同じ軸がC版で既に13.6%を実現している。
鈴木さんのご指摘(「上限一桁を切り捨てず確実な足場を固めたうえで
進むべき」)が正しい。命令あたりコストの削減とレーン利用率の向上は
競合せず効果は乗算であり、足場を先に固める方針を採る。

## 393-8. local→shared移行(案①)を却下する

**結論: 妙案は存在するが、実行する価値がない。** 却下理由を実測から
記録する。

**理由1: スタックはすでにL1に常駐している。**

```
1SMあたり常駐warp数 ≈ 6.05(393-9参照)
6.05 warp × 32 thread × 208 B = 40,269 B ≈ 40 KB
sm_86 の L1/shared 統合キャッシュ = 128 KB/SM
```

「535M local sectorsが発生しているのに`long_scoreboard`が5.58%止まり」
という一見不可解な観測の答えがこれである。sharedへ移してもレイテンシ
階級は変わらない。

**理由2: フレーム圧縮は最もホットな領域に命令を足す。**
N=21なら21bit×4+5bit=89bitで12バイトに収まる理屈だが、push/popの
たびにシフト・マスクが増える。C版が`STL.128`1本にまとめて勝っている
のと真逆の方向であり、D+E(全体の32.9%)を悪化させる。

**理由3: 393-9の方向と真っ向から競合する。** 占有率を上げれば
208 B/threadのフットプリントが線形に増え、shared(100 KB上限)にも
L1(128 KB)にも載らなくなる。①は「効果ゼロで、伸びしろを潰す」変更で
ある。

**本項目をここでクローズする。**

## 393-9. 最大の発見 — グリッドがハード容量の12.6%しか要求していない

`Active Warps Per Scheduler = 1.51`。この数字の出所を計算で追う:

```
484 blocks × 32 threads = 1 warp/block × 484 warps(グリッド全体)
1.51 = 484 / (SM数 × 4 scheduler)   →   SM数 ≈ 80
```

ncuの報告と突き合わせる:

| | 値 |
|---|---:|
| ハード上限(`GPU Maximum Warps Per Scheduler`) | 12 |
| この起動構成で許される上限(`Theoretical`) | 4 |
| **実測(`Active`)** | **1.51** |

BLOCK=32は1ブロック=1warpであり、sm_86の「1SMあたり16ブロック」制限に
よって`Theoretical`が4に張り付く。そして実測1.51は**構成が許す上限の
38%、ハード上限の12.6%**でしかない。

**同時に、warp間の負荷不均衡は実質ゼロであることも確定した。**
1.51 / (484/320) = 1.51/1.5125 = **99.8%**。484個のwarpはほぼ全員が
launchの最後まで生き残っている。**損失は100%がwarp内(レーン間)である。**
375-382のフレームキュー・ワークスティーリングが31%退行して閉じた理由も
これで説明がつく——盗む相手(遊んでいるwarp)が存在しなかった。

実効スレッド稼働率:

```
C版   = (1.51/12) × (10.13/32) = 3.98%
Codon = (1.53/12) × ( 7.17/32) = 2.86%
```

**A10Gの96%が遊んでいる。そのうちレーン発散が説明するのは約1/8で、
残り約7/8は「グリッドが12.6%しか席を要求していない」ことである。**

### なぜ見落とされていたか

READMEの237前後の記録に`block=32、max_blocks=484`が「A10G単GPUの実測
best flow」とある。ただしこれは**K-batching導入(292)より前**の記録で
ある。292以前は`threads × 1 = chunk`だったのでグリッド規模とチャンク
サイズは同一のノブだった。292でK軸が分離した後、**スイープされたのは
Kだけ**である。この軸は少なくとも陳腐化しており、現在の意味では一度も
探索されていない可能性が高い。

### L1フットプリントが天井を決める

| 構成 | スレッド数 | warp/SM | L1のスタック占有 | 判定 |
|---|---:|---:|---:|---|
| 現行 484×32 | 15,488 | 6.05 | 40 KB / 128 KB | 席が余っている |
| **1280×32** | **40,960** | **16** | **104 KB / 128 KB** | **ぎりぎり載る** |
| 3600×32 | 115,200 | 45 | 299 KB / 128 KB | 破綻 |

そして **40,960 threads × K=48 = 1,966,080 ≈ N=21の全タスク
2,025,282(97%)**。K=48を変えずに、N=21が1launchで完結し常駐warpが
2.65倍になる。C側の変更は`const int MAX_BLOCKS = 484;` の1行のみ。

## 393-10. 本番C経路が並べ替えパイプラインを捨てている

stage 3のログとソースの両方から確認した。

```
[crunner-input-reuse] N=21 filtered_bin=constellations_N21_6.bin.soa_ref_361.bin.maxd14only_363.bin
```

`ensure_crunner_input_bin(N, stream_fname, ...)`に渡される`stream_fname`は
`ensure_constellations_bin_stream()`が返す**生の**`constellations_N21_6.bin`
である。361のSoAダンプも363のフィルタもこの生の順序に対して走っており、

捨てているもの(いずれもCodon経路での実測値):

| 並べ替え | 実測利得 |
|---|---:|
| w3_j7(330-333) | -1.294% |
| bucket_run=2048(344) | -4.111% |
| isort9(350) | -0.82% |

`CHUNKSHAPE148_LANE_COUNT=32` / `lanephase32`という名のとおり、この
並べ替えは**warp内32レーンへのタスク配置を制御するもの**である。
393-9で「warp間の不均衡はゼロ、損失は全部warp内」と確定した以上、
