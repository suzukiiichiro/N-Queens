## 395b — 明示スタックのトップフレームをレジスタ常駐化(+ 4.2%の謎の切り分け)

### 恒久ルール(395b以降、鈴木さんのご指示): 確定パラメータは`-g`の初期値

確定したパラメータは`A10G_FINAL_DEFAULT_*`(および`CRUNNER_INPUT_ORDER`)に
置き、`-g`が適用する値そのものにする。395bで2点を揃えた:

1. **`A10G_FINAL_DEFAULT_*`の適用条件を`argc==2`→`argc<=4`へ**。従来
   `-g 21 21`はローカル初期値のまま`bench_mode=0`(旧Codon経路、484×32、
   生順)へ落ちていた(395a r1のGセルが測ってしまった経路)。395bからは
   `-g 21 21` = **本番構成をN=21に限定**。nmaxより後ろの位置引数による
   上書きは従来どおり(`-g 21 21 32 484 0 0 5 0`で旧経路に到達可能)。
   395aPyからのコア差分 `added=18 removed=2`(この1点のみ)。
2. **C側バイナリ自身の`NQ_MAX_BLOCKS`既定も484→800**。環境変数未設定の
   直接実行でも確定構成で走る(`395b_validate.sh`が`[gpu-config]`で確認)。
   395aからのコード領域差分 removed=18 added=46(レジスタトップ+この既定)。

現時点の確定値: `BLOCK=32`、`MAX_BLOCKS=800`、`bench_mode=37`、
`preset=7`、入力順`sched`(394f L3)。以後、新しい確定値が出るたびに
同じ場所を更新する。

### カーネル変更(`395b_kernel_maxd14.cu`、395a r2からコード領域 removed=15 added=40)

`process_one_task()`の3箇所(root高速経路のpush、pop、主ループのpush)。
スタックのトップフレームを`top0/top1`(レジスタ)に置く:

- **push**: `save_sp != 0`なら旧トップをローカルメモリへspill(`STL.128`、
  従来と同じ1本)、新フレームをレジスタトップへ。
- **pop**: レジスタトップから`cur_*`を復元し、`save_sp != 0`なら下の
  フレームを`LDL.128`で先読みしてトップへ。**この`LDL`の結果を読むのは
  次のpopかpush**——ノード展開1回分(30命令以上)後なので、レイテンシが
  臨界パスから外れる。
- `save_sp`=生きているフレーム数(レジスタトップ含む)、`stack_ptr =
  2*(save_sp−1)`。フレーム形式・26スロット配列・pushガードの形
  (358/359 RISK NOTE)・全分岐の形は不変。メモリに落ちるのは最大12フレーム。

394aの根拠: popの`LDL`消費(`LOP3.LUT R0, R7, mask`)が`long_scoreboard`の
100.0%(全サンプルの6.8%)を占め、ロードと消費の間に独立命令が2つしか
なかった。395aの教訓(命令数削減は無効)を踏まえ、**命令数ではなく
臨界パス上のレイテンシ**を減らす変更である。

**GPU前の等価性(サンドボックス)**: CPUハーネスで実データ2,048件+別
スライス1,024件のper-record結果が394g/395aとバイト一致。ハーネスも
2,048件のゲートを再実行する。

### 事前登録予測(実測前に固定)

1. I0: **バイト一致**(主予測、確度70%)。一致ならI1≈I2(±1%)で「経路」が
   原因。不一致ならI1がI2より3%以上速く「ファイル」が原因。
2. **K1 vs K0: −2%〜−5%。** 反証条件: K1 ≥ K0−0.5%。その場合、popの
   レイテンシも臨界パス上では隣のストールに吸収されている(=カーネル内
   の局所最適化はこの領域でほぼ無効)と結論し、カーネル側の残る手を
   395c(pop→decode直結、`B3`段の除去=再収束バリアの削減)に絞る。
3. NCU=1: `long_scoreboard`の割合6.8% → **2%以下**、`LDL`は1本のまま。
4. GはK1±1%、Aは191,781±1.5%。
5. CPUハーネス2,048件ゲート通過(等価性)。
