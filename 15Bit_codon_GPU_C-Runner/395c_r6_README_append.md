## 395c-r6 — r5の413 msを本番既定として採用する

### r5で確定したこと

事前登録6件すべて成立、全セル `total_sum=314666222712` MATCH、全セル1710 MHz。

| セル | 構成 | free_mb | kernel_ms | G0比 |
|---|---|---:|---:|---:|
| G0 | `-g 21 21`、追加なし | 22,018 | 133,585.359 | — |
| Gh | + 遊休ホルダー1本 | 21,762 | 133,179.047 | −0.304% |
| Gx | + `NQ_EXTRA_CTX=1` | 21,762 | 133,206.172 | −0.284% |
| Gxb | Gxの複製 | 21,762 | 133,172.016 | −0.309% |

`|Gx − Gh| = 0.020%`。**別プロセスのコンテキストと自プロセスのコンテキストは、
本番経路でも区別がつかない。** G0は前日のr3 Gp（133,585.188）を **+0.0001%**
で再現しており、条件を固定したこの環境の再現性は0.01%台である。

主張ルール（実測前に固定した `≥0.20%` かつ複製が0.05%以内）を満たした。
**利得 0.309%、413 ms。**

### r6が変えるもの — 実行行1行

ディスパッチテーブルの項目を次の形にする。

```
CRunnerEntry(14,"./395c_r6_kernel_maxd14","NQ_EXTRA_CTX=1 ",...)
```

**処遇はバイナリの既定値ではなく `env_prefix` に置く。** 理由は記録である。
`env_prefix` に置けば `[crunner-config] env_prefix=` と `dispatch.log` に
必ず残り、どの走行がどの状態だったかを後から追える。バイナリ既定を1にすると
追えなくなる。`NQ_EXTRA_CTX` は未設定時0のままなので、**直接実行は従来どおり
で、対照として使い続けられる**。

- `395c_r6_kernel_maxd14.cu`: r4のリネーム。最初の `#include` 以降は
  **バイト一致**（ハーネスがコード領域全体のsha256でゲートする。カーネル
  領域だけではない）。差分はヘッダのコメントのみ。
- `395c_r6Py_kernel_maxd14_final.py`: r5Pyからの差分は、コメントを除いた
  **実行行で3行**（`VERSION_TAG`、`REV_TAG`、テーブル1行）。

### セル — 交互配置

| セル | ディスパッチャ | 期待 extra_ctx | 期待 free_mb |
|---|---|---:|---:|
| Gb1 | `395c_r5Py_…`（処遇なし） | 0 | 22,018 |
| Gn1 | `395c_r6Py_…`（env_prefix） | 1 | 21,763 |
| Gb2 | r5 | 0 | 22,018 |
| Gn2 | r6 | 1 | 21,763 |

約11分。ベースラインにr5ディスパッチャを使うのは、**それがG0を出した現物
だから**である。新しい対照を作らずに済む。交互に走らせることで、セッション
内のドリフトが平均で相殺される。

### 事前登録予測（実測前に固定）

1. **S1**: `|Gb1 − Gb2| ≤ 0.05%`、かつ両者が 133,585 の ±0.1%、
   `free_mb`=22,018、`extra_ctx`=0。ベースラインが安定で、r5が測ったのと
   同じ状態であること。
2. **S2**: `|Gn1 − Gn2| ≤ 0.05%`、`free_mb`=21,763、`extra_ctx`=1。
3. **S3**: `mean(Gn) ≤ mean(Gb) − 0.25%`。
4. **S4**: `dispatch.log` に `env_prefix=NQ_EXTRA_CTX=1`、CRunnerログに
   `[gpu-ctx] extra_ctx=1`。**反証**: prefixは出ているのに `extra_ctx=0` が
   バイナリに届いている場合、テーブルの `env_prefix` がコマンド行に反映されて
   おらず、本リビジョンは無効。

**採用ルール**: S1〜S4がすべて成立し、実測利得が **0.25%以上** のときのみ
採用する。下回ればテーブルをr5の形（`./395c_r4_kernel_maxd14`、`env_prefix`
空）へ差し戻す。**セッション内の交互A/Bを生き延びない利得は利得ではない。**

### 本リビジョンが扱わないこと

他のNでの正当性は検証しない。採用の前に一度、

```
SMALL_N=1 bash 395c_r6_validate.sh
```

を走らせること（`-g 5 15` の正当性専用セルが加わる）。既定で無効にしてあるのは、
小さいNの入力が未キャッシュだと所要時間が読めず、本ハーネスを11分に保てなく
なるためである。

### 記録すべき脆弱性 — 意図的に残す

r5の掃引で、速い領域は**浅い盆地ではなく幅128 MiB未満の鋭い切り欠き**である
ことが分かった。

| 追加占有 | free_mb | kernel_ms |
|---:|---:|---:|
| +0 MB | 22,018 | 133,561 |
| +128 MB | 21,890 | 133,993 |
| **+255 MB** | **21,762** | **133,181** |
| +384 MB | 21,634 | 134,074 |
| +512 MB | 21,506 | 133,854 |
| +1,024 MB | 20,994 | 134,310 |

**両隣は「何も足さない」状態より遅い。** 谷に入れているのは、このドライバで
コンテキスト1個がちょうど255 MiBを占めるからにすぎない。したがってこの413 msは
原理ではなく本構成固有の値である。

- ドライバ更新でコンテキストあたりのオーバーヘッドが変われば谷は動く
- **本バイナリ自身のデバイスメモリ使用量が変わっても谷から外れる**

**N=22/23のmaxd16は確実に後者に当たる。** 移行前に必ず測り直すこと。

### 位置づけ

残り8.3%に対して0.31%、27分の1である。2:02への道ではない。この一連の
リビジョンの実質的な成果は、むしろ次の3点にある。

- ノイズフロアが0.012〜0.026%になった。394cの±1.6%は占有状態が未管理だった
  ことの帰結であり、機構の揺らぎではなかった
- 条件を固定すればセッションをまたいで0.0001%で再現する
- CRunnerのメモリ使用量が性能に非線形かつ鋭敏に効くことが分かった。
  maxd16へ進む前に、この軸を必ず測る

```
STATIC_ONLY=1 bash 395c_r6_validate.sh   # OK=27
              bash 395c_r6_validate.sh   # ビルド → Gb1 Gn1 Gb2 Gn2、約13分
SMALL_N=1     bash 395c_r6_validate.sh   # 採用前に一度、-g 5 15 の正当性も
```

**事前条件**: `395c_r5Py_kernel_maxd14_final`（ベースライン用、r5でビルド済み）と
`395c_r4_kernel_maxd14`（r5テーブルの参照先）が残っていること。どちらも
ハーネスが冒頭で存在確認する。
