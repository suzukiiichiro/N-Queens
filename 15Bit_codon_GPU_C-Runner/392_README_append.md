## 392: maxd16のCUDA Cポート

**位置づけ**: 段取り2(390_maxd16_kernel_port_spec.mdに基づくCポート)。
`389_kernel_maxd14.cu`(364の直系)を土台に、機械的な置換で作成した。

**やったこと**:

- `389_kernel_maxd14.cu`の全文をベースに、`MAXD14_ANCESTOR`(13)→
  `MAXD16_ANCESTOR`(15)とカーネル関数名の置換のみで`392_kernel_
  maxd16.cu`を生成。**スクリプトで逆置換し、意味的な差分が
  `#define`の値`13→15`ただ1箇所であることを確認済み**。
- 出力マーカーは389と同一(`[gpu-run-done]`/`[gpu-run-correctness]`)
  のまま——382のhybrid版のように別タグにはしていない。同じ
  single-shot grid-stride構成の延長であり、`crunner_dispatch_table()`
  側は既にログファイル名でバイナリごとに名前空間を分けているため、
  新しいパース処理は不要という判断。

**このサンドボックスで実際に確認できたこと**(gccが使えたため):

- CPU専用テストパス(`gcc -x c ... -lm`)が実際にコンパイル成功、
  `-Wall -Wextra`で警告ゼロ。
- **副産物**: 364/388/389が文書化していたビルドコマンドの`-x c`の
  位置に既存のバグを発見。`-x c`をソースファイルより後ろに置くと
  (364/388/389のヘッダーに書かれている順序そのもの)、このサンドボックス
  のgcc 13.3.0では失敗する(`file format not recognized; treating as
  linker script`)。**389自身の実ファイルでも同じ現象を再現確認した**
  ので、391以前から引き継がれていた文書上の問題。392のヘッダーでは
  正しい順序(`-x c`を先に)に直し、この発見を記録した。389側は今回は
  未修正(必要であれば別途)。

**意図的にやっていないこと**:

- 実機`nvcc`ビルドはまだ未実施(このサンドボックスにCUDAツールチェーン
  が無いため)。
- **`crunner_dispatch_table()`への登録は保留**。登録するとbare `-g`が
  自動的にN=23本実行まで進んでしまい、「N21のncu高速化が一段落する
  まではN23実行を保留する」という合意した段取りに反するため。
- N=23実データでのC版CPU検証は行わない(鈴木さんのご判断: 391で
  Codon版は既にGPU/CPU双方で実機検証済み、392はbyte-diffで機械的に
  正しさが保証されているため、二重の検証コストより段取り3(N21の
  ncuプロファイリング)を優先)。

**事前予測**: 実機で`nvcc -O3 -arch=sm_86`ビルドが成功する、と予測する
(コード領域が389と機械的に一致しているため)。

**結果**: (鈴木さんの実機実行後、ここに追記。今回は**ビルドのみ**の
確認で、実行はしない)
