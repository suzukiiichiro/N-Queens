## 401-r3 — 401-r2を実測で閉じる（決定セル、L1内の傾き、N=20の食い違い）

### 401-r2はどこまで走ったか

`N_LIST="19 20"` 相当で実行され、**決定セル（M3: N=21のMB=800対1280）は
未実行**でした。走った分だけで、M2は反証されています。

| N | k@10 w/SM → k@16 w/SM | MB=1280の罰則 |
|---:|---:|---:|
| 19 | 35.0 → 21.9 | +53.33% |
| 20 | 53.5 → 33.4 | **+71.72%** |

予測は「Nが上がりkが増えれば罰則は縮む」でしたが、**拡大**しました。N=20の
16ワープ段（k=33.4）はN=19のベースライン段（k=35.0）とほぼ同じkなのに、罰則は
N=19より大きい。**`k_per_thread` はこの罰則の機構ではありません。** 交絡説は外れです。
全8セル `total_sum` MATCH、反復幅 0.004〜0.099%。

### r2のログにあった、未解明の食い違い

同一セッション・同一バイナリ・同一入力・`extra_ctx` 合計3・`free_mb=21,776` まで
一致しているのに、N=20で

| 経路 | kernel_ms |
|---|---:|
| ディスパッチャ `-g 20 20`（親ctx + `NQ_EXTRA_CTX=1`） | 16,480.3 |
| 直接 `NQ_EXTRA_CTX=2`（r2の梯子のアンカー） | **17,378.4（+5.5%）** |

397のV4「直接＋`NQ_EXTRA_CTX=2` は本番状態を再現する」は **N=21でしか確認されて
いません**（E0=133,155 対 G=133,19x、差0.02%）。N=19では逆に直接が −0.6%。
400〜401でN=19/20の直接セルから引いた相対比較は、この正体不明の状態の上に
載っています。402がN=19/20をデバッグ規模に使うなら、先に潰す必要があります。

### r3が測る3つのこと — コード変更ゼロ

**(A) M3をN=21で実測して閉じる。** MB=800 対 1280（16 w/SM、104 KB、k=49.4）。
N=19/20の傾向を外挿すれば約85%で、結論は読めていますが、この案件は外挿で軸を
閉じません。各1回、約6分です。

**(B) 402の前提を、現行バイナリ・N=21で初めて測る。** 402（104バイト詰め替え）
の根拠は「L1に収まっている限りワープ増は効く」という394gの傾き
（484→704→800→968 で −23.7% / −4.6% / +11.3%）です。しかしそれは当時の
バイナリ・入力順・484基準の測定で、**現在の800の両隣はN=21で一度も測られて
いません。** r3は MB=720（9 w/SM、58.5 KB）と MB=880（11 w/SM、71.5 KB——401の
L1曲線ではまだ ≥99% ヒット）を置きます。720が800より遅くなければ、L1内でも
ワープ増は既に効いておらず、詰め替えは書く前に計画し直しです。

**(C) N=20の食い違いを交互3セルで切り分ける。**

| セル | 経路 | ctx数 | 期待 free_mb |
|---|---|---:|---:|
| Gd | `-g 20 20`（ディスパッチャ） | 3 | 21,776 |
| Dx2 | 直接 `NQ_EXTRA_CTX=2` | 3 | 21,776 |
| Dh | 直接 `NQ_EXTRA_CTX=1` ＋ 外部ホルダー1本（`395c_ctx_holder`、0 MB） | 3 | 21,776 |

Gd→Dx2→Dh を2周。どれとどれが一致するかで、402以降のデバッグ規模セルを
どの経路で走らせるべきかが決まります。

### `*_README_append.md` との照合

- (A)(B): 394b/r2（968→1280 で +54.7%）、394g（484〜968の掃引、800を最良点として
  採用）、401（N=19の梯子とL1曲線）、401-r2（N=19/20）に該当あり。
  **N=21での800の両隣（720/880）と1280は未測定。**
- (C): 395c-r4（M1=D1、自プロセスctxと他プロセスctxは0.001%で区別不能）、
  397 V4、398 W1 に該当あり。**いずれもN=21のみ。N=20での成立は「該当なし」。**

### セルと所要

| フェーズ | 内容 | 目安 |
|---|---|---|
| 0 | 静的ゲート、ビルド（CRunner、ホルダー、Codon） | 3分 |
| B | N=20: Gd Dx2 Dh Gd Dx2 Dh | 3分 |
| A | N=21: G21（`-g 21 21`、本番アンカー兼入力の所在確認）→ 直接 MB=720 800 880 1280、各1回、`NQ_EXTRA_CTX=2` | 13分 |

通しで約20分。全セルの直前に**GPU空きゲート**（`compute-apps` にホルダー以外の

### 事前登録予測（実測前に固定）

1. **R0**: G21 が 133,192 の ±0.10%、`extra_ctx=1`。本番アンカー。
2. **R1（ハードゲート）**: 直接 N=21 MB=800 が 133,197 の ±0.15%（398 W1の
   アンカー）、`free_mb=21,762`、`extra_ctx=2`。**落ちたらN=21の直接セルは比較
   不能で、R2〜R4は読みません。**
3. **R2**: N=21 MB=1280 の罰則 ≥ 20%（点予想 約85%）。成立すればM3/M4は
   **「L1の外側のオカパンシー軸は死」** で決着。20%未満なら401-r2のM4に従い、
   この段にもう1リビジョンの価値があります。
4. **R3（表明する予測）**: N=21 MB=720 は MB=800 より **+1.5〜+6%** 遅い
   （394gの8→10段が −4.6%）。**反証条件**: 720が ±0.3% 以内か速い → L1内の
   傾きは10ワープで既に寝ており、**402の前提が弱まる**。詰め替えを書く前に
   計画を見直します。
5. **R4（表明する予測）**: N=21 MB=880 は MB=800 より遅い（N=19で71.5 KBは
   +6.8%）。成立なら、実効L1予算は401の「71.5 KB」ではなく **65 KB側で
   見積もる**べきで、104バイトなら **20 w/SM**（22ではない）。880が0.3%超で
   速ければ、800はL1の天井ではなく402は無料の一段を得ます——ただし1回の実測では
   採用せず、**交互A/Bの候補として記録**するに留めます。
6. **R5（表明する予測、確信は弱い）**: N=20の差は再現する（Dx2 − Gd ≥ +3%）。
   ホルダー方式 Dh は **ディスパッチャ側（Gd）に一致する**と予想します。
   - Dh ≈ Gd → N=20では自プロセスの `cuCtxCreate` と他プロセスのコンテキストが
     等価でない。395c-r4のM1=D1はN=21固有。**ルール**: デバッグ規模の直接セルは
     ホルダー方式で走らせる。
   - Dh ≈ Dx2 → 直接実行は両方式とも遅く、ディスパッチャ経路がctx数と`free_mb`
     以外の何かを持っている。**ルール**: 原因が分かるまでデバッグ規模の時間測定は
     `-g` 経由。
   - **反証条件**: 3セルが0.1%以内で一致 → r2の17,378はセッションの人工物で、
     V4はN=20でも成立。
   - 決定則: 差が1%以上残るなら、上のルールを恒久ルールに昇格します。

### 本リビジョンが変えないもの

本番既定は一切変えません。`-g 21 21` の期待値は **133,192 ms** のままです。

### 402への接続

r3の結果で402の形が決まります。

- R2成立・R3成立 → **402は104バイト詰め替え**（`bit(21)+rd_lost(3)+avail(21)+depth(4)`）。
  397を止めたのと同じ**全2,025,282レコードのバイト一致ゲート**を最初に置き、
  掃引は MB=800 / 1120 / 1600（104 Bなら1600が 20 w/SM・65 KB＝今日の足跡のまま
  ワープ2倍）。R4の結果で予算の上限（20か22か）を決めます。
- R3反証 → 詰め替えは保留。ワープを増やしても効かない機構を先に特定します
  （`wait` 48% を依存鎖側から）。
- R5の結果 → 402以降のデバッグ規模セルの経路を固定します。
