## 395c — 395bを差し戻し(カーネル=395a r2)、起動経路の約4%を説明する

### 変更

- `395c_kernel_maxd14.cu`: **カーネル領域は395a r2とsha256一致**(395bの
  レジスタトップは除去)。ホスト側の既定`NQ_MAX_BLOCKS=800`(395bの
  恒久ルール)は維持。395aからのコード領域差分 removed=3 added=6(既定のみ)。
- `395cPy`: 395bPyの純粋リネーム(テーブルのみ)。395bの`argc<=4`ゲート・
  800・sched・リダイレクトはそのまま。
- `395c_ctx_holder.cu`: CUDAコンテキスト(+任意サイズのデバイス確保)を
  N秒保持するだけのプログラム。

### 測定設計(カーネルは変数ではない)

| セル | 内容 | 期待 |
|---|---|---:|
| D0 | 直接、GPU上に他プロセスなし | ≈139,166(395b I1) |
| **D1** | 直接、**別プロセスが素のCUDAコンテキストを保持**(0 MB) | H_ctxなら ≈133.6 |
| **D2** | 直接、別プロセスがコンテキスト+**2,048 MB**をtouch済みで保持 | H_placeならD1と≠ |
| G | `-g 21 21`(ディスパッチャ、`-d`なし、sched再生成込み) | ≈133,577(395aのG)= 差し戻しの確認 |
| A | 484 | ≈191,781(395aのA) |

各セルの実行中、5秒ごとに`nvidia-smi`でSMクロック・電力・温度を採取し、
平均/最小を報告する(**H_clock**: 直接実行中だけクロックが落ちている
可能性を実測で排除する)。

### 事前登録予測(実測前に固定)

1. GはH_ctxの有無によらず395aのG(133,577)を±1.5%で再現——差し戻しが
   効いていることの確認。D0は139,166±1%。
2. **H_ctx(主仮説)**: D1 ≤ D0 −3%。「別プロセスのコンテキストが
   存在する」だけで同じ実行が約4%速くなる。反証条件: D1がD0±1%なら、
   Codon親が「コンテキスト保持」以外に行っていること(環境変数、cwd、
   stdioの向き先、プロセス階層)が原因で、395c-r2でディスパッチャの
   コマンド行を二分探索する。
3. H_place: |D2 − D1| ≥ 1.5%なら、デバイスメモリの配置(他プロセスの
   確保で自プロセスの領域がずれること)が上乗せで効いている。
4. H_clock: D0とGの実行中平均SMクロックが2%以上違えばクロック効果。
   1710で一致なら除外。

### 意味

この4%は本番`-g`が既に得ている値だが、**機構が分かれば直接実行でも
再現でき(測定の悲観バイアスが消える)、かつ配置由来なら意図的な配置
制御でさらに取れる可能性がある**。968の崖の縁での±1.6%のセッション間
変動(394c)も同じ機構かもしれない。

```
STATIC_ONLY=1 bash 395c_validate.sh      # OK=24(カーネル領域=395a r2、指紋3/6、top0不在 等)
              bash 395c_validate.sh      # CPU等価 → D0 D1 D2 → G A、約15分
```
