## 4. 覚えておくと役立つ小さな教訓

- **CRunner入力ファイルは2段パイプライン**: 生のstream binでは
  ダメで、`dump_soa_reference_c_port()`(361)→外部
  `363_filter_maxd14_only.py`の2段を経た7フィールド/28バイト形式が
  必要(385 r1でこれを見落とし、40分の空振りをした)。389で自動構築
  (`ensure_crunner_input_bin()`)を実装済み。
- **CPU側の独立検証実装は並列化必須**: 391 r1で、単一スレッドの
  CPU参照実装が原因で1万件処理に20分以上かかり停止しているように
  見えた(GPU自体はとっくに終わっていた)。`@par`で修正。今後
  同様のCPU参照実装を書くときは必ず並列化を最初から入れること。
- **gccの`-x c`はソースファイルより前に置く**: 364/388/389の
  ヘッダーに書かれている`gcc ... -o out file.cu -x c -lm`という順序は、
  少なくともgcc 13.3.0では失敗する(`file format not recognized`)。
  正しくは`gcc ... -x c -o out file.cu -lm`。392で気づいて記録、
  389側は未修正のまま。
- **Rev毎に完結した管理**: 鈴木さんの明示的な方針として、内容が同じ
  でも`.cu`ファイルやログディレクトリ名は毎回のリビジョン番号を
  冠する(`REV_TAG`定数、388で導入・以後389/391で継続)。過去の
  リビジョン名を「流用」しない。
- **maxd16は「深さの違いだけ」**: 現存の古い`kernel_dfs_iter_gpu_
  maxd16`はmaxd14作成時の未更新コピーだったため、ベースにしては
  いけなかった。必ず現行の最適化済みmaxd14から機械的に導出すること
  (スクリプトでの逆置換diff確認が有効)。
- **段階的検証(小規模→大規模)**: N=23全件(4,427万件)のような
  未検証の大規模実行の前に、10/50/200/1000件のような小さい段階を
  昇順に踏み、都度Ctrl+Cできるようにしておくと安全(391で確立した
  パターン)。
