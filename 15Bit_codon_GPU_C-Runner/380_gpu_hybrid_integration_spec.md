# 380_gpu_hybrid_integration_spec.md

## rev380 — ハイブリッド設計の実GPUカーネル統合、設計仕様
## (設計専用リビジョン。374のカーネルへのコード変更ゼロ)

362→363、376→377、378→379と同じ「設計→実装」分離パターンを踏襲。
379bでCPU上で実測・確認できたハイブリッド設計(ローカルスタック主体+
閾値K超過時のみ共有キュー)を、初めて実GPUカーネルへ統合するための
設計をここで固める。実装は381以降に分離する。

---

## 1. 現行(374)カーネルの構造

`kernel_dfs_iter_gpu_maxd14`(537-570行目)は極めてシンプル: 32×484
=15,488スレッドがgrid-strideループでM件のタスクを分担し、各スレッドが
`process_one_task()`(ローカルスタックのみ、atomicなし)を順次呼んで
`thread_total`に加算、最後に`results[tid]`へ書き出すだけ。共有状態は
一切ない。

---

## 2. 380で追加が必要な要素

### 2.1 デバイス側データ構造

379a/377aで確立した`FQSlot`/`FrameQueue`/`TaskSchedule`/`Frame`の
定義とVyukovキューのpush/pop実装は、`HOSTDEV`(`__host__ __device__`)
マクロで既にデュアルビルド対応済みであり、**ロジックの変更なしに
そのままデバイスコードとして使える**。追加が必要なのは:

```c
__device__ FQSlot*  g_queue_buf;
__device__ uint32_t g_queue_capacity_mask;
__device__ uint64_t g_enqueue_pos;
__device__ uint64_t g_dequeue_pos;
__device__ int      g_active_workers;
__device__ TaskSchedule* g_schedules;   // M件分、ホストでcudaMalloc
```
(またはFrameQueue構造体1つをdevice グローバル変数として持ち、
ポインタ経由で渡す形でも良い——実装時に決める)

### 2.2 カーネルを2段に分割

CUDAにはグリッド全体のバリアが(cooperative groupsを使わない限り)
無いため、「全M件のシード完了」と「ワーカー開始」の間に確実な同期点を
置くには、**カーネルを2つに分ける**のが最も単純で安全:

**カーネル1: `seed_kernel_maxd14`(新規)**
- 起動形状: grid-strideでM件を分担(既存のgrid-stride形状を流用可)
- 各スレッドが担当タスクについて`seed_task()`(377b/379aで確立、
  ロジック変更なし)を呼び、`TaskSchedule[i]`を埋め、0〜2個の初期
  Frameを`g_queue`へpush
- カーネル完了 = 暗黙のグリッド全体同期(ホスト側で
  `cudaDeviceSynchronize()`を挟むか、単に2つ目のカーネル起動が
  1つ目の完了を待つCUDAのデフォルト挙動に任せる)

**カーネル2: `kernel_dfs_hybrid_maxd14`(新規、374本体の代替)**
- 起動形状: 374と同じ32×484=15,488スレッド(**grid-strideループは
  廃止**——各スレッドはpersistent workerとして、キューが尽きるまで
  働き続ける)
- 各スレッドが`LocalStack`(374の`stack[MAXD14_ANCESTOR*2]`と同じ
  サイズ、レジスタ/ローカルメモリ)を1つ持ち、`run_hybrid_episode()`
  (379aで確立、ロジック変更なし)をキューから引いたFrameに対して
  繰り返し呼ぶ
- 終了判定は379aと同じ(`g_active_workers==0 && キュー空`)

### 2.3 374との差分は「起動形状の意味」だけ

重要な点: `process_one_task()`本体のロジック・`seed_task()`・
`run_hybrid_episode()`のビット演算は、377a〜379aで**1バイトも
変えていない**。380が新規に書くのは、(a) 2つのカーネルのラッパー
(グローバル変数へのアクセス、キューの初期化)、(b) ホスト側の
`cudaMalloc`/2段階カーネル起動シーケンスだけである。

## 3. メモリ容量の見積もり

377cの実測(実データ)から、`FQSlot`は32B/スロット。379bの実測:

| K | 200件でのtotal_frames |
|---|---|
| 1 | 35,769,530 |
| 4 | 10,733,397 |
| 8 | 6,035,104 |
| 13以上 | 200(≒タスク数) |

N=21全量(M=2,025,282、200件の約10,126倍)に単純比例で外挿すると、
K=1では**3620億フレーム相当**になり得る——これは現実的でない。
**380の初回GPU実験はK=13(またはそれに近い高い値)から始めるべき**
であり、Kを下げる実験は容量を実測しながら慎重に進める必要がある
(379bの「同一データセットで段階的に確認」という方法論をGPU上でも
踏襲する)。

A10Gの24GBを踏まえ、K=13なら数百万スロット(32B×数百万=100MB
程度)で十分足りるはずだが、Kを下げる実験に進む際は都度実測して
容量を決める。379cのような「容量固定で桁違いに足りず即オーバー
フロー」を繰り返さないよう、**まず小さいM(374同様、部分実行や
N=18スケールのデータ)で実測してから全量M=2,025,282へ拡大する**
段取りを組む。

## 4. GPU特有のリスク要因(正直に書いておく)

- **atomic競合の桁違いの差**: 379bのCPU実験は8スレッドでの競合
  だったが、GPUは15,488スレッドが同時に同じ`FrameQueue`のCAS
  ループへアクセスし得る。CPU実験で得られた「Kごとの傾向」が
  GPUでも同じ形になるかは**未検証**——競合パターンが全く異なる
  可能性がある。
- **warp発散**: 「ローカルにpushするか、閾値超過で共有キューへ
  回すか」という分岐は、同一warp内の32レーンで足並みが揃わない
  場合に発散を招く。K=13(ほぼ374相当)ではこの分岐がほぼ常に
  「ローカルへ」側になるはずなので発散は最小限のはずだが、Kを
  下げるとこの発散自体が新たなコストになり得る。
- **2カーネル構成のオーバーヘッド**: seed_kernelとhybrid_kernelの
  2回のカーネル起動+その間の暗黙的な同期は、374の単発カーネル
  起動と比べてわずかなオーバーヘッドを追加する。K=13での実測が
  374とほぼ同タイムなら許容範囲、明確に劣化するなら見直しが必要。

これらは実装前には理論的に予測しきれず、**実測が必須**である
(378仕様で確立した姿勢をそのまま継承)。

## 5. 実装・検証計画(381以降)

358/359・377b/cの教訓を踏まえ、以下の順で段階的リスク低減を図る:

1. **381a**: seed_kernel + hybrid_kernelの2段構成を実装。**K=13固定**
   で、374と同じ実データ・同じオラクル(`314666222712`)との一致を
   まず確認する。これは「新しいインフラ(2段カーネル+キュー)が
   正しく動くこと」だけを検証する回で、速度向上は一切期待しない
   ——むしろ374よりわずかに遅くても(2カーネル起動のオーバーヘッド
   分)問題ない。
2. **381b**: 正当性が確定してから、`kernel_ms`をcudaEventで計測し
   374(`kernel_ms≈201,232ms`、373の新環境参照値)と比較。この時点
   で初めて速度についての判断材料が揃う。
3. **381c以降**: 381bの結果を見て、Kを下げる実験(379bと同じ手法
   をGPU上で)に進むか、あるいはK=13付近で留まる(共有キュー機構
   自体のオーバーヘッドが利益を上回ると分かった場合)かを判断する。

**正当性確認は必ずタイミング計測より先に行う**——このプロジェクト
全体を通して確立された原則を、GPU初挑戦のこの局面でも徹底する。

---

## 6. まとめ

379bでCPU上で実測・確認したハイブリッド設計を、374のカーネルには
一切手を加えず、2段カーネル構成(seed_kernel + hybrid_kernel)として
GPUへ統合する設計を示した。ロジック(`process_one_task`/`seed_task`/
`run_hybrid_episode`)は377a〜379aで確立したものをそのまま流用する。
GPU特有のatomic競合・warp発散のリスクは実測でしか判断できないため、
381でK=13固定の正当性確認から慎重に始める計画とした。
