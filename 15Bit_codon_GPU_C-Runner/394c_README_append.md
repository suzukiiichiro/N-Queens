## 394c — 本番CRunnerに並べ替え済みbinを投入する`bench_mode=39`

### 動機(393-10)

本番C経路(`bench_mode=37`)は`ensure_crunner_input_bin()`に**生の**
stream binを渡しており、330-350のホスト側並べ替え(w3_j7 −1.29%、
bucket_run=2048 −4.11%、isort9 −0.82%、いずれもCodon経路での実測)を
一度も通っていない。この並べ替えは`lanephase32`という名のとおり
**warp内32レーンへのタスク配置**を決めるもので、393-9/394aで「損失は
すべてwarp内」と確定した以上、まさに効くべき対策である。並べ替えは
タスク集合の順列(333)なので、オラクル`314666222712`は不変。

### 変更内容(Codon側、394bPyからのコア差分 `added=117 removed=3`)

新しい`bench_mode=39`。`bench_mode=37`のCRunnerディスパッチと**1点だけ**
違い、`ensure_crunner_input_bin()`に渡すファイルがchunkshape148済みbin
(mode 30/31がCodonカーネルで走らせているもの)になる。

- base/shaped binの解決と未生成時の構築は、mode 30/31の文を**逐語
  コピー**(30/31側は無変更。リファクタしない——単一変数の規律)
- 並べ替えパラメータはmode 30/31と同じグローバル(w3_j7、bucket_run=2048、
  isort9、variant=2)= 採用済み本番値。`argv[5]=484`なら既存キャッシュ
  `…_b32_m484_s15488_run2048_isort9.bin`をそのまま再利用する
- **順列ガード**: `shaped_records != stream_records`なら停止(GPU未起動)
- **stride結合**: 並べ替え単位は`BLOCK*MAX_BLOCKS`(`argv[4]*argv[5]`)。
  C側のstrideがこれと一致しないとレーン配置が壊れるので、mode 39は
  `env_prefix`経由で`NQ_MAX_BLOCKS={gpu_max_blocks}`をC側に渡す
  (`crunner_run()`は既に`f"{env_prefix}{binary_path} …"`で組み立てる)。
  **argv[5]が並べ替えstrideと起動strideの唯一の出所**になる
- CLIホワイトリスト/presetゲートに39を追加(361/365/366/368/369/385/391
  で7回踏んだ罠。`394c_validate.sh`が静的にゲート、負のテスト済み)
- `crunner_dispatch_table()`は`./394c_kernel_maxd14`を参照、`env_prefix`は
  空のまま(bare `-g`とmode 37は484×32のまま)
- `394c_kernel_maxd14.cu`は394bのヘッダーのみリネーム(コード領域sha256
  一致、`394c_validate.sh`がゲート)

### 設計: 2×2要因計画(348と同じ形)

| | 生入力(mode 37) | 並べ替え入力(mode 39) |
|---|---|---|
| **MAX_BLOCKS=484** | **A**(=389アンカー) | **B** |
| **MAX_BLOCKS=968** | **C**(=394b r1点) | **D** |

- A vs B: 本番strideでの並べ替え効果(**394cの問い**)
- C vs D: 394b r1最適点での並べ替え効果
- A vs C: MAX_BLOCKS効果・生(394bの再現)
- B vs D: MAX_BLOCKS効果・並べ替え
- A vs D: 両方

Dは初回のみstride 30,976向けの並べ替えbinを生成する(N=21で数分)。
各セルN=21フル、オラクルゲート、C側の`[gpu-run-done]`末尾の`stride=`が
意図値と一致することもゲート(環境変数を無視する古いバイナリの誤読
防止)。所要約15分+D初回の生成。

### 事前登録予測(実測前に固定)

1. **A**は389アンカー201,237 msを±1%で、**C**は394b r1の163,185 msを
   ±1%で再現する。
2. **B vs A: −3%〜−6%。** 反証条件: |Δ| ≤ 1%なら、並べ替えの効きは
   Codon版SASS固有のものでC版には転移しない。その場合、Codon経路で
   採用済みの並べ替え軸(330-350)は本番C経路では意味を持たず、以後は
   C版でのレーン配置設計を別途行う。
3. **D vs C: B vs Aと同符号、大きさは±3ポイント以内。** isort9(−0.82%)
   はK=48の周回列に結びついたものでstride 30,976(K=66)には転移しない
   可能性があるため、Dの効果はBよりやや小さいと見る。
4. 全セルでオラクル一致(順列)。

### 実行手順

```
STATIC_ONLY=1 bash 394c_validate.sh     # 静的17項目(39のゲート、37無変更、.cu領域一致)
              bash 394c_validate.sh     # A B C D(約15分+D初回生成)
STAGES=A,B    bash 394c_validate.sh     # 394cの問いだけ(約7分)
```

sudo不要。

  最適点をブラケットしてから、両方を同時に1トークンずつ
  (`A10G_FINAL_DEFAULT_MAX_BLOCKS`と`bench_mode`既定)で行う。

  二重計算除去)へ進む。


## 394c 結果(確定)・並べ替え入力は本番strideで**+29.7%悪化**、968では−1.0%

**実行完了。** 4セルすべてオラクル一致、stride結合ゲート全通過(C側実測
strideが意図値と一致)。SMクロック1710MHz。

| | 生入力(mode 37) | 並べ替え入力(mode 39) |
|---|---:|---:|
| **MAX_BLOCKS=484** | **A 201,236 ms**(389比−0.001%) | **B 261,060 ms(A比 +29.7%)** |
| **MAX_BLOCKS=968** | **C 160,528 ms** | **D 158,955 ms(C比 −1.0%)** |

- A vs C(MAX_BLOCKS効果、生): **−20.2%**(394bの−18.9%を再現方向で確認)
- B vs D(MAX_BLOCKS効果、並べ替え): −39.1%
- A vs D(両方): **−21.0%** — 現時点の最速セル。N=21 ≈ 2:39

### 事前登録予測の判定

| # | 予測 | 実測 | 判定 |
|---|---|---|---|
| 1 | A/Cがアンカー±1% | A −0.001% / **C −1.6%**(394b r1/r2の163,185/163,060/163,197比) | A的中、**C外れ** |
| 2 | **B vs A: −3〜−6%** | **+29.7%** | **反証(逆符号・5倍)** |
| 3 | D vs C: Bと同符号、±3pt以内 | −1.0%(Bは+29.7%) | **反証** |
| 4 | 全セルでオラクル一致 | 一致 | 的中 |

予測2の反証条件は「|Δ| ≤ 1%なら転移しない」だったが、起きたのは
「逆方向に、この計画全体で最大の効果」である。**カーネルを1バイトも
変えずに、データの順序だけでC版が30%動く。** 順序は本番C経路における
第一級のレバーであることが判明した——ただし今のところ悪い方向に。

### 交絡: Dでは`iter_sort`が無効化されていた

Dの並べ替え生成ログ:

```
[chunkshape148-warning] group too large for stable packing: n=1486848 cap=1048576; iter_sort disabled for this group
```

stride 30,976ではchunkshape148のグループ(48×30,976 = 1,486,848)が
`CHUNKSHAPE148_SORT_SEQ_BITS=20`のcap(1,048,576)を超え、**isort9が
主グループで無効化**された。つまり:

- B(484): broadmarktail + scorestripe + bucket_run=2048 + **isort9 あり** → +29.7%
- D(968): broadmarktail + scorestripe + bucket_run=2048 + **isort なし** → −1.0%

strideとiter_sortが交絡しており、+29.7%をどの段に帰属させるか、この
要因計画だけでは決まらない。ただし「Dで無効化されていた段」がまさに
per-thread列の並べ替え(345-350: 「sort SCOPEが機構」、K=48のlaunch
単位・チャンク境界の暗黙同期を前提に設計)であり、C版の単一launch
131周回にはその前提がない。**H_isort**(isort9が原因)を394dの主仮説と
する。

### Cの−1.6%について(記録)

C=160,528は394b r1/r2の968(163,185 / 163,060 / 163,197)より1.6%速い。
同一バイナリコード・同一入力(`[crunner-input-reuse]`)・同一stride・
1710MHz。484側は3セッションで±0.003%に収まっているのに対し、968側は
セッション間で±1.6%動く。968はL1の崖の縁(394b r2)で動作しており、
ブロック配置(968 = 80×12+8、8個のSMが13ブロック)への感度が高いと
解釈する。**本番採用点は縁より少し下(r3: 864〜928)を選ぶ根拠**にも
なる。

### 案①・並べ替え軸の扱い

並べ替え軸はクローズしない——+30%の効果を説明せずに閉じるのは、
逆方向に同程度の余地がある可能性を捨てることになる。394dで分解する。
