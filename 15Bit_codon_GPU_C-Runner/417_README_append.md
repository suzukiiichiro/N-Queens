## 417 — N=25：配置 425 を 16 段（192 B）にして auto を 425 に、N=25 の入力を作る

### preset_queens の罠（`.py` 側の本体）

`select_dynamic_preset_queens` は N≥25 で **8** を返していた（`-g` の既定 `A10G_FINAL_DEFAULT_PRESET=7` を無視）。8 で生成すると `constellations_N25_8.bin` は
約 10⁹ 件（preset が 1 増えると件数は約 9.4 倍：N=21(6) 2.0M → N=22(7) 28.7M。同 preset では N+1 で 1.5 倍）。sched ファイル 26 GB、394f の RSS は
N=24 の 9.5 GB から約 135 GB——30 GB の機械では不可能。**7 のまま**なら約 10⁸ 件（×1.5）で、`required_maxd = N − preset − 1 = 17`
（21→14、23→15、24→16 の規則）。`.py` の 2 行で N=25 も 7 にする（N=26・27 は 8 のまま。そこは sched のチャンク化と一緒に考える）。

| auto | N=24 → 424 | **N=25 → 425**（N=24 は 424 のまま、`<424>` は 15 段・SASS 不変） |

### 独立参照 `417_ref_dfs.c`（392 の代わり）

392（16 B フレーム、15 段）は N=25（深さ 17）を回せない。代わりに **スケジュール前計算と 1 歩の算術（nld／nrd／ncol／nf、MARK_T64）だけを共有し、
スタックの仕組み（push／pop・フレーム・死にビット・root 高速路・`cur_x`）を一切持たない素直な再帰 DFS** を C で書いた（OpenMP、CLI と出力は CPU ハーネスと同じ）。
これが検証するのは配置のスタック機構——392 が 402〜424 に対して検証していたのと同じもの。スケジュールの意味論は 391 で Codon GPU と一致済みで配置に依らない。

手元：N=21／23／24 の合成レコードで 415＝416＝ref（バイト一致）、**N=25（深さ 17＝16 段を全て使う、1,500 件、1,158 件が非ゼロ、マーク連鎖 688 件）で 417 auto(425)＝ref（total 208,443,471）**。
417 は N=21／23／24 でも 415 と一致、`NQ_LAYOUT=425` の N=24（16 段）も一致。rc=3：N=26、424@25、423@24。
ハーネスでは **実データ N=24 で ref＝392（Y2r、ハード）を先に確かめてから** N=25 の参照に使う。
