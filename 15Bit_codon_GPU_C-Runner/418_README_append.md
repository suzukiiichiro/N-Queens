## 418 — 入力分割走行（チャンク＝チェックポイント、複数 GPU 並列）、カーネル変更なし

### 根拠

CRunner のカーネルは **1 回の grid-stride 起動**で、スレッド t がレコード t, t+S, t+2S, …（S = BLOCK×MAX_BLOCKS = 32×960 = **30,720**）を足し込み、results.bin（スレッドあたり u64、245,760 B）に書く。入力を **S の倍数の位置で切った連続チャンク**では、チャンク内の局所番号 j と全体番号 o+j が S を法として同じなので、チャンクのスレッド t は一括走行のスレッド t の項のうちチャンク内に落ちるものを正確に持つ。したがって **チャンクごとの results.bin を要素ごとに足すと、一括走行の results.bin とバイト一致する**（u64 の整数加算は順序に依らない）。

これで `.cu` を一行も変えずに：(a) **チェックポイント**（喪失は最大 1 チャンク）、(b) **複数 GPU 並列**（ワーカーごとに `CUDA_VISIBLE_DEVICES`）、(c) **N=26/27 で不可避の入力分割**の土台、が得られる。古い 111Py の multigpu_worker（`-g … 29 8 7 0 k 4`）は現系統には無いので、同等の口を外側のスクリプトとして作った。

### 事前登録（利得は主張しない。本番値は不変）

- **W1 分割の費用** ＝ Σkernel_ms（分割）／kernel_ms（一括）：**x4 で 1.02〜1.07、x8 で 1.04〜1.10**。根拠：チャンクの尾は相対的に長い。N=25 の尾は 202 h の約 5%（GPU 等価で約 1.8% の損）、1 スレッドあたり件数 n の 1/√n で伸びると見ると、N=23（1,442 件/スレッド）の x4（360）で約 +4%、x8（180）で約 +6%。**反証：x8 > 1.15**（分割の前提が崩れている、またはチャンク間の仕事量が極端に偏っている）。
- **W2 4 GPU の壁時計加速** ＝ 一括 kernel_ms ÷ 分割の壁時計 ≥ **3.4 倍**（x4・x8 とも）。
- **W3** G0〜G3 の kernel_ms が互いに 1% 以内（4 枚の A10G は同速）。
- **N=25 の CHUNKS**：W1(x8) ≤ W1(x4)＋0.03 なら 8、そうでなければ 4。
- 採用則：ハード全通過で 418 が本番バイナリ／.py（SASS 同一、N≤24 の本番値不変）。
