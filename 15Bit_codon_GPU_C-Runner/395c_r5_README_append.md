## 395c-r5 — r4の−0.30%を本番`-g`経路に持っていく

### r4で決着したモデル

コンテキストは「数」ではなく**閾値**である。

| free_mb | 1 ctx | 2 ctx | 3 ctx | 5 ctx | 7 ctx |
|---:|---:|---:|---:|---:|---:|
| 22,018 | 147,807 (S255) | 133,561 (D1) / 133,563 (M1) | — | — | — |
| 21,762 | — | **133,181** (Y510) | 133,201 (X2b) | — | — |
| ~21.0–21.5k | — | 133,854 / 134,310 | — | 138,174 (X4) | 137,404 (X6) |

1個は遅い。2〜3個が最適。5個以上でまた悪化。そして**自プロセス内で
`cuCtxCreate` した遊休コンテキストは、別プロセスのホルダーと区別がつかない**
——M1 = 133,562.562 対 D1 = 133,561.062、133,561分の1.5 ms（+0.0011%）。

2コンテキスト下での追加占有量は浅い最小を持つ。

| 素のctxを超える占有 | kernel_ms | D1比 |
|---:|---:|---:|
| 0 MB | 133,561.1 | — |
| **255 MB** | **133,180.7** | **−0.285%** |
| 512 MB | 133,854.0 | +0.219% |
| 1,024 MB | 134,310.0 | +0.561% |
| 2,048 MB | 147,634.8 | +10.537%（崖は1,024〜2,048） |

現行本番は「Codon親(255 MiB) + CRunner」＝2コンテキスト・`free_mb` 22,018 で
**133,585.188**。最適点は `free_mb` ≈ 21,763 で、約400 ms下にある。到達には
**コンテキストを1個増やすだけでよく、明示的なメモリ確保は要らない**
——コンテキスト自体が255 MiBを持ち込むからである。

### 本リビジョンが測るもの

その状態への**独立した2経路**を、本物の`-g`経路上で測る。

- **Gh**: `-g` の傍らで遊休ホルダーを1本走らせる —— **コード変更ゼロ**
- **Gx**: `NQ_EXTRA_CTX=1` をCRunnerに届かせる —— **ヘルパープロセス不要**

両者とも `free_mb` 21,763・3コンテキストに着地するはずで、したがって
**同じ値**を出さねばならない。この一致自体がモデルの検定になる。

カーネル変更なし、ホスト変更もなし。バイナリはr4のもの、Codonソースは
395cPyの純粋リネームで、コード領域の編集は `VERSION_TAG`・`REV_TAG`・
ディスパッチテーブル1行とそのコメントのみ（**removed=3 added=9**）。
`env_prefix` は空のままにしてある——1つのテーブル項目が両経路に使え、
`NQ_EXTRA_CTX` は呼び出し側の環境から渡せる（`os.system` は環境を継承する）。

### セル

| セル | 構成 | 期待 free_mb |
|---|---|---:|
| G0 | `-g 21 21`、追加なし（アンカー） | 22,018 |
| **Gh** | `-g 21 21` + 遊休ホルダー1本 | 21,763 |
| **Gx** | `-g 21 21` + `NQ_EXTRA_CTX=1` | 21,763 |
| Gxb | Gxの複製（本番値の主張根拠） | 21,763 |
| F128 | 直接、ホルダー1個×128MB | — |
| F384 | 直接、ホルダー1個×384MB | — |

### 事前登録予測（実測前に固定）

1. **R1**: `G0` は 133,585 の ±0.5%、かつ `free_mb` = 22,018 → リネームも
   r4バイナリも本番経路上で不活性。**これが落ちたら以下は解釈不能**。
2. **R2**: `Gh` は 133,201 の ±0.15% → コード変更ゼロの経路が効く。
3. **R3**: `Gx` は 133,190 の ±0.15%、かつCRunnerログに
   `[gpu-ctx] extra_ctx=1` が出る → 環境変数が子まで届き、ヘルパー不要の
   経路が効く。**反証**: `extra_ctx=0` が出た場合、ディスパッチャは環境を
   通しておらず、経路(b)はテーブルの `env_prefix` 経由にする必要がある。
4. **R4**: `|Gx − Gh| ≤ 0.05%` かつ両者の `free_mb` が21,763 → 2経路は
   同一のデバイス状態に到達する。これより大きくずれるなら、「追加
   コンテキストは所有者を問わない」というモデルはまだ何かを取りこぼしている。
5. **R5**: `Gxb` は `Gx` の ±0.05%。
6. **R6**: `F128 ≥ 133,181` かつ `F384 ≥ 133,181` → +255 MBが局所最適で
   ある。いずれかが 133,150 を下回れば最小はそこではなく、+160〜+320 MBの
   細かい掃引をr6で行う価値がある。

### 主張ルール（実測前に固定）

利得を主張するのは以下の**両方**が成り立つときに限る。

```
(G0 − min(Gh, Gx, Gxb)) / G0 ≥ 0.20%   かつ   |Gxb − Gx| ≤ 0.05%
```

これを下回れば、r4の−0.30%はセッション間の人工物であったということであり、
**本番は現状のままとする**。ハーネスがこの判定を自動で出す。

### 注意

r5は本番の既定値を変更しない。どちらの経路を採用するかはr6で決める。
`NQ_EXTRA_CTX` は現時点では診断用の環境変数であり、既定は0（未設定時に
コンテキストを一切作らない）である。

```
STATIC_ONLY=1 bash 395c_r5_validate.sh   # OK=23（Py差分3/9、カーネルsha不変、stderr捕捉の確認 等）
              bash 395c_r5_validate.sh   # codonビルド → G0 Gh Gx Gxb F128 F384、約21分
```

**事前条件**: sched入力、`rev386_validation_helpers.py`、`395c_r4_kernel_maxd14.cu`、
`395c_ctx_holder.cu` が揃っていること。`REV_TAG` が変わるので CRunner ログは
`395c_r5_crunner_logs/` に出る（ハーネスがタールボールへ収める）。
