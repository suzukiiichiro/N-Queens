### カーネル変更(`395a_kernel_maxd14.cu`、394gからコード領域 removed=3 added=12)

394a(`-lineinfo` SourceCounters)で、`nibble_op`の抽出(`cur_depth<8`判定・
シフト・選択、5 SASS)がfuture_check直前で**再実体化**されており、その
重複が全サンプルの**4.09%**を占めていた(ncuの行帰属でL478/479/481の
SASSが2箇所に存在することを確認済み)。原因は最初の抽出レジスタが
`nibble_op & 7`で上書きされること。

変更: 抽出直後に`block_code = nibble_op & 7u`と`fc_flag = nibble_op & 8u`
を取り、2つの消費側(block_code分岐、future_check)がそれぞれを読む。
`nibble_op`自体は以後読まれない。意味は同一(同じnibbleの同じビット)。
pushガード(358/359のRISK NOTE)には触れていない。

**GPU前の等価性確認(サンドボックスで実施済み、ハーネスでも再実行)**:
CPUテストハーネス(`gcc -x c`は`process_one_task()`そのものをコンパイル
する)で、実データ先頭**2,048件のper-record結果が394gとバイト一致**。

## 395a r2 — 64bitスケジュールの1回シフト(ファイル名は同じ、内容をr2に)

`process_one_task()`で、precompute後に`schedule64 = (hi<<32)|lo`を
ループ不変量として1回作り、主ループのnibble抽出を
`(uint32_t)(schedule64 >> (cur_depth*4)) & 15u`の**1回のfunnel shift+AND**
にする(`cur_depth*4 ≤ 52 < 64`)。`cur_depth<8`の判定・2本のシフト・
選択が消える。r1のhoistは残す。rootの高速経路(`schedule_lo & 15u`)と
pushガードは無変更。394gからのコード領域差分 removed=9 added=22。

**GPU前の等価性(サンドボックス)**: CPUハーネスで実データ2,048件
+別スライス1,024件のper-record結果が394gとバイト一致。

### 事前登録予測(r2、実測前に固定)

1. K0は139,404±1%(r1で±0.03%再現済み)。
2. **K1 vs K0: −1.5%〜−4%。** 反証条件: K1 ≥ K0−0.5%なら、nvccが
   64bitシフトをfunnel shiftに落としていない(SASSで確認)か、そもそも
   抽出コストがサンプルの主因ではなかった。
3. G(明示800/37/sched)はK1±1%。Aは197,792±1.5%。
4. NCU=1: SASS命令数460〜468、`ISETP.GE.AND P0, PT, R7, 0x8`は**0回**、
   代わりに`SHF.R.U64`系が主ループに現れる。
5. FULL_G=1: N=21・N=22ともオラクル一致、stride 25,600、入力
   `.sched394f.bin`。N=22の`kernel_ms`は初測定(389期の484/生:
   約1,699,210 ms)。

### カーネル変更(r2)の判定

予測2(−1.5〜−4%)は**反証**(−0.2%)。NCU=1のSASS: 命令数**472で不変**、
`ISETP.GE.AND P0, PT, R7, 0x8`は**0回**(予測どおり述語ペアは消えた)、
しかし`SHF.R.U64`が**2回**(289650: 2,060M実行、289950: 2,021M実行)
——**nvccは依然として抽出を再実体化している**(funnel shiftとして)。
ストール内訳も394aと同一(wait 42.7 / br_res 24.4 / long_sb 6.8%)。

**教訓(記録)**: IPC 0.28のストール律速領域では、ALU命令を減らしても
臨界パスは短くならず、サンプルは隣の命令へ移るだけである。394aで
「重複が全サンプルの4.09%」と書いたのは*注目の配分*の上限であって
*時間*の上限ではなかった。C版がCodon版より命令数29%減で13.6%しか
速くなかったこと(393-7)と同じ現象。395bは命令数ではなく
**臨界パス上のレイテンシ**(popの`LDL`消費)を狙う。r2の変更は
再現性のある−0.2%・オラクル一致・CPU等価なので**維持**する。

### 本番経路の到達点

`-g 21 21 32 800 0 0 7 37`(bare `-g`がN=21で適用する値)で
**133,580 ms = 2:13.6、389アンカー201,237比 −33.6%**。目標2:02.52
(122,520 ms)への残り**−8.3%**。鈴木さんのbare `-g`(r2バイナリ、N=5..20
の後)では135,961(1.8%上)——800の配置感度と同じ幅。

### 未解明: G は K1 より 4.2% 速い

同じバイナリ・同じstride(25,600)なのに、Gの入力
(`…maxd14only_363.bin.sched394f.bin`、本番パイプラインが395aツールで生成)は
K1の入力(`394f_input_L3_sched.bin`、394fが旧ツールで生成)より**4.2%速い**
(2回とも)。484でも同じ: A=191,780 vs 394fのL3@484=197,792(−3.0%)。
両ファイルは同じ生ファイルの同じ安定ソートで**バイト一致するはず**
(ツールの新旧キーは順序同値、合成データで一致を確認済み)であり、
`[permute-done]`の隣接ペア数も両方2,013,988で一致している。
残る候補は「ファイルが違う」か「起動経路(Codon親プロセスが生きている)
が違う」か。**推測せず、395bのStage Iで`cmp`と直接実行で決める。**

N=22のbare `-g`は`rc=2`(=SIGINT、Ctrl-C)で中断されていた——失敗では
ない。N=22の800×schedは未測定のまま。
