## 391: maxd16カーネルの段階的GPU-CPU突き合わせ

**位置づけ**: 「N=23全件(4,427万レコード)は一度も検証していないカーネル
に数時間かけて賭ける形になるのでは」というご指摘への対応。いきなり
本番実行に進まず、規模を段階的に上げながら都度報告する仕組みを追加した。
390(maxd16カーネル本体の新規実装)に続くもので、**390自体もこの
391も、実機コンパイルはまだ一度も通っていない**——今回が両方の初回
実機テストになる。

**新設した仕組み**:

1. `process_one_task_maxd16_cpu()`: `kernel_dfs_iter_gpu_maxd16`(390)の
   ループ本体から、**手作業ではなくPythonスクリプトで機械的に**導出した
   スカラー・CPU専用・単一タスク版参照実装。grid-strideの外枠を
   取り除き、4箇所の早期終了を`return`に置き換えただけ。364自身の
   `process_one_task()`(CでのCPU検証用)と同じ関係を、Codon側・
   maxd16版で再現したもの。
2. `maxd16_staged_gpu_cpu_xcheck()`: レコード数
   [10000, 50000, 100000, 200000]を昇順に実行。**各段階ごとに結果行を
   出力してから次へ進む**——GPU合計とCPU独立参照実装の合計を突き合わせ、
   不一致があれば即座に停止。段階ごとに自然なCtrl+Cのタイミングができ、
   途中で止めても進捗が残る。
3. 新設`bench_mode=38`として配線。

**実行コマンド**:
```bash
./391Py_kernel_maxd14_final -g 23 23 32 484 1 0 7 38
```

**事前予測**: 4段階すべてで`match=YES`になり、`[maxd16-xcheck-done]`
まで到達する、と予測する。もしどこかで`match=NO`が出たら、
390_maxd16_kernel_port_spec.mdの核心的主張(depth非依存)の再検証が
必要になる——単純な打ち間違いと決めつけない。所要時間は、各段階が
N=21全件(2,025,282件、約3〜4分)よりずっと小さい規模なので、
4段階合計でもそれよりかなり短時間で終わるはず、と予測する。

## 【r2訂正】CPU側ループが単一スレッドでハング

r1のCPU側ループ(`process_one_task_maxd16_cpu`を呼ぶ部分)は単純な
単一スレッドの`while`ループだった。実機でN=23・段階1(1万件)を実行
したところ20分以上出力ゼロのまま止まっているように見え、`nvidia-smi`
で確認したところGPU使用率は0%(アイドル水準)——GPUカーネル自体は
とっくに終わっており、**単一スレッドのCPU側ループがボトルネックに
なっていた**。364自身のヘッダーコメントが既に警告していた通り
(「単一CPUスレッドで、GPUが15,488並列でやることを直列にやると、
この作業負荷では基本的に4〜5桁遅い」)。鈴木さんはCtrl+Cで安全に
中断(実害なし)。

**r2の修正**:

- CPU側ループを`@par`(`build_soa_for_range`が`w_arr`の充填に既に
  使っているのと同じ並列forパターン)で結果配列に書き込む形に変更。
- 既定の段階数を`[10000,50000,100000,200000]`から`[10,50,200,1000]`
  へ大幅に縮小(このマシンでの実際の所要時間がまだ未計測なため、
  当て推量の新しい既定値を置くより安全側に倒した)。
- 各段階の出力を`gpu_elapsed`/`cpu_elapsed`に分離(以前は合算のみ)、
  今後の段階サイズ判断が憶測ではなく実測に基づけるようにした。
- `391_validate.sh`のビルド・実行コマンドの先頭に`stdbuf -oL -eL`を
  追加(パイプ経由だと出力がバッファリングされ、実際は進んでいても
  何も表示されない状態になりうるため)。

**結果(r2)**: 2026-09-07、cudacodon実機で`bash 391_validate.sh`実行、
`OK=11 FAIL=0`で`391 PASSED`(実行時間`real 1m19.571s`)。

**確定**: 新しいmaxd16カーネル(390)は、独立したCPU参照実装
(`process_one_task_maxd16_cpu`)と4段階すべてで完全に一致した。
390_maxd16_kernel_port_spec.mdの核心的主張(depth非依存)は、静的な
分析だけでなく実機でも裏付けられた。

**タイミングの観察**(今後の段階サイズ判断のため記録):
CPU側(`@par`並列化後)はmの増加に対してGPU側よりずっと急激に時間が
伸びる(200→1000の5倍で、CPU時間は約5.5倍)。単純に外挿すると、
N=23全件(4,427万件)をCPU側でも突き合わせようとすると非現実的な
時間になる——これは想定通りで、CPU突き合わせは小規模での正しさ確認
専用であり、N=23全件の本実行はGPU単独(CPU突き合わせなし)で行う
設計が正しいことの裏付けになった。GPU側はこの規模(10〜1000件)では
まだ固定オーバーヘッドが支配的で、mに応じた増加はほとんど見えない。
