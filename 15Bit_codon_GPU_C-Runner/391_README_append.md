## 391: maxd16カーネルの段階的GPU-CPU突き合わせ

**位置づけ**: 「N=23全件(4,427万レコード)は一度も検証していないカーネル
に数時間かけて賭ける形になるのでは」というご指摘への対応。いきなり
本番実行に進まず、規模を段階的に上げながら都度報告する仕組みを追加した。
390(maxd16カーネル本体の新規実装)に続くもので、**390自体もこの
391も、実機コンパイルはまだ一度も通っていない**——今回が両方の初回
実機テストになる。

**新設した仕組み**:

1. `process_one_task_maxd16_cpu()`: `kernel_dfs_iter_gpu_maxd16`(390)の
   ループ本体から、**手作業ではなくPythonスクリプトで機械的に**導出した
   スカラー・CPU専用・単一タスク版参照実装。grid-strideの外枠を
   取り除き、4箇所の早期終了を`return`に置き換えただけ。364自身の
   `process_one_task()`(CでのCPU検証用)と同じ関係を、Codon側・
   maxd16版で再現したもの。
2. `maxd16_staged_gpu_cpu_xcheck()`: レコード数
   [10000, 50000, 100000, 200000]を昇順に実行。**各段階ごとに結果行を
   出力してから次へ進む**——GPU合計とCPU独立参照実装の合計を突き合わせ、
   不一致があれば即座に停止。段階ごとに自然なCtrl+Cのタイミングができ、
   途中で止めても進捗が残る。
3. 新設`bench_mode=38`として配線。

**実行コマンド**:
```bash
./391Py_kernel_maxd14_final -g 23 23 32 484 1 0 7 38
```

**事前予測**: 4段階すべてで`match=YES`になり、`[maxd16-xcheck-done]`
まで到達する、と予測する。もしどこかで`match=NO`が出たら、
390_maxd16_kernel_port_spec.mdの核心的主張(depth非依存)の再検証が
必要になる——単純な打ち間違いと決めつけない。所要時間は、各段階が
N=21全件(2,025,282件、約3〜4分)よりずっと小さい規模なので、
4段階合計でもそれよりかなり短時間で終わるはず、と予測する。
