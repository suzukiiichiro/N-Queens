## 396-r2 — 代理を作り直し、順位表は必ず出す

### 396のT1は設計どおりに落ちた

切り詰め代理は、本番の 65.7647 µs/record に対して全滅だった。

| k | records | kernel_ms | µs/record | dev |
|---:|---:|---:|---:|---:|
| 1 | 25,600 | 1,471.159 | 57.467 | −12.62% |
| 2 | 51,200 | 2,631.016 | 51.387 | −21.86% |
| 4 | 102,400 | 5,007.200 | 48.898 | −25.65% |
| 8 | 204,800 | 11,317.858 | 55.263 | −15.97% |
| 16 | 409,600 | 21,262.502 | 51.910 | −21.07% |

**13〜26%安く、しかもkに対して非単調。** プレフィックス総和を差分すると
理由が出る。

| ラウンド範囲 | ms/round |
|---|---:|
| 0 | 1,471.2 |
| 1 | 1,159.9 |
| 2–3 | 1,188.1 |
| 4–7 | 1,577.7 |
| 8–15 | 1,243.1 |
| **16–79.11** | **1,773.5** |
| 全体平均 | 1,683.6 |

**394fのスケジュールはレコードを並べ替えている。** ファイルの先頭は安い
部分で、コストは後半が担っている。**ソート済みファイルのプレフィックスは
標本ではない。** あの代理でプロファイルを取っていれば、自信に満ちた誤った
順位表が出ていた。ゲートが仕事をした。

### r2の代理 — 層化ラウンド抽出

1ラウンド = 25,600レコード = stride 25,600 でちょうど全スレッド1周ぶんである。
**ラウンド単位で抜けば、レコードとスレッドの対応が完全に保たれ、warp内の
分岐パターンもそのまま維持される。** 変わるのはループ回数だけ。

先頭k個ではなく、全79ラウンドに等間隔で散らしたk個を取る。

| k | 抽出ラウンド |
|---:|---|
| 2 | 0, 78 |
| 4 | 0, 26, 52, 78 |
| 8 | 0, 11, 22, 33, 45, 56, 67, 78 |
| 16 | 0, 5, 10, …, 73, 78 |

### フォールバック — 順位表を人質にしない

層化でも較正に落ちた場合、ハーネスは**実物のフル入力を、1セクションずつ、
時間予算のもとでプロファイルする**。順序は `WarpStateStats` を先頭に置く
（U5がこのリビジョンの本題だから）。セクションごとにタイムアウト（既定900秒）、
全体予算（既定2400秒）。**予算内に完了したセクションだけを報告する。**

396の成果物はストール順位表であって、代理の設計問題でそれが得られないのは
本末転倒である。`FORCE_FULL=1` で最初からこちらを選ぶこともできる。

### 事前登録予測（実測前に固定）

1. **U1**: 層化 k ∈ {4, 8, 16} のいずれかで µs/record が 65.7647 の ±1% に
   入る。上のラウンドコスト模型からの**予測値**は
   **k=4: 66.33（+0.85%）、k=8: 65.21（−0.84%）、k=16: 65.47（−0.45%）**、
   **k=2 は −3.64% で外れる**。
   模型は rounds 16–79 を一様と仮定した粗いものなので、実測がこれから外れる
   こと自体は模型の粗さを示すだけで、方法の否定にはならない。だからこそ
   フェーズ2でプロファイルを直接測る。
2. **U2**: 単一ラウンドのコストは位置に対して単調ではなく、
   **round ≥ 16 が round < 16 より一貫して高い**。round 0,10,…,70 の8点で
   確認する（各約1.5秒）。
3. **U3**: アンカー `-g 21 21` が 133,192.071 の ±0.1%、`extra_ctx=1`。
4. **U4**: メモリスループットはピークの5%未満。
5. **U5（本題）**: 支配的なwarpストール理由は**分岐解決系で25%以上**。
   **反証されれば律速要因は移動しており、397は最適化ファミリを変える。**
   ハーネスは順位表の直後にこの判定を出す。

### 四点の同一性

- `396_r2_kernel_maxd14.cu`: 396のリネーム。コード領域全体 sha256
  `c5dbde3f1002229b…` が一致。カーネル領域は395a r2以来不変
  （`ebd7f523deb59134…`）。
- `396_r2Py_kernel_maxd14_final.py`: 396Pyからの差分は**実行行3行**。
  `env_prefix="NQ_EXTRA_CTX=1 "` は維持。

```
STATIC_ONLY=1 bash 396_r2_validate.sh   # OK=16
              bash 396_r2_validate.sh
FORCE_FULL=1  bash 396_r2_validate.sh   # 代理を試さずフル入力で
SKIP_ANCHOR=1 bash 396_r2_validate.sh   # アンカー2.5分を省く(非推奨)
```

### 副次的な観察 — 記録に留める

ラウンドコストが位置によって 1,160 〜 1,774 ms（**1.53倍**）も違うという
事実そのものは、394fスケジュールの性質として記録しておく価値がある。ただし
**全スレッドが全ラウンドを1つずつ処理するので、この偏りが負荷不均衡を生む
ことはない**。フェーズ2の8点測定は、この分布の形を初めて直接見ることになる。
