## 395c-r3 — 二因子を分離する(占有量か、第二コンテキストか)

### ここまでで確定していること

395c(2026-09-08)と r2(2026-09-09)。全セル `total_sum=314666222712` MATCH、
全セル `sm_mean = sm_min = 1710 MHz`。

| 他プロセスの占有 | free_mb | kernel_ms | 占有なし比 |
|---:|---:|---:|---:|
| 0 MiB | 22,273 | 139,177.4 | — |
| 255 MiB(ctxのみ) | 22,018 | 133,561.1 | **−4.035%** |
| 2,303 MiB | 19,970 | 147,634.8 | **+6.077%** |
| ディスパッチャ `-g 21 21` | — | 133,576.3 | 255 MiB行と0.002%一致 |

r2はセル順を反転し、5セルすべてを **0.015%以内**で再現した。セッション温度は
10℃高かった(53〜56℃ → 62〜67℃)。**実行順も熱も除外**。セッション内反復
ノイズは 0.012% / 0.003%。

r2の配置プローブは**配置説を否定した**。D0rとD0r2はバッファの相対レイアウト
が異なる(ctrl0が −0x10800000 と −0x16800000)のに0.012%しか違わず、逆に
D0r2とD2rはレイアウトが同一なのに6%違う。仮想アドレスは時間を予測しない。
予測するのは他プロセスの占有だけで、しかも**非単調**(0=遅い、255 MiB=速い、
2,303 MiB=最も遅い)。単一因子ではこの形は作れない。よって二因子:

- **因子A: 第二のCUDAコンテキストが存在する** → **−4.04%**(二値)
- **因子B: デバイスメモリが占有されている** → **2 GBあたり +10.54%**(単調)

### 本リビジョンが割る分岐

外部ホルダーは因子AとBを**同時に**変える(コンテキストを作り、かつ約255 MiBを
占有する)。したがって −4.04% はどちらの寄与か未定である。`NQ_PAD_MB` は
**自プロセスに**同じ量を確保させる——第二コンテキストなしで、因子Bだけを動かす。

- `S255` が 139,177 付近 → 占有だけでは何も起きない。**因子Aはコンテキスト**。
  レバーは補助プロセス(本番はすでに持っている)であり、プロセス内パッド掃引は
  無意味になる。
- `S255` が 133,561 付近 → **因子Aは占有量**。レバーは自プロセス内にあり、
  133,561より良い点を探すパッド掃引が次の一手になる。

### セル(順序はもはや変数ではない——r2が決着させた)

| セル | 条件 | 期待 free_mb |
|---|---|---:|
| **S255** | 直接、`NQ_PAD_MB=255`、他プロセスなし | 22,018 |
| S2303 | 直接、`NQ_PAD_MB=2303`、他プロセスなし | 19,970 |
| A0 | 直接、パッドなし、他プロセスなし(セッション内アンカー) | 22,273 |
| X2 | 直接、ホルダー**2個**(各0 MB) | — |
| B512 | 直接、ホルダー1個(512 MB) | — |
| Gp | `./395cPy_kernel_maxd14_final -g 21 21`、実行中2秒ごとにcompute-apps採取 | — |

`free_mb` は「処遇が実際にデバイスまで届いたか」のゲートとして使う(±2 MiB)。

- `395c_r3_kernel_maxd14.cu`: r2に **`NQ_PAD_MB` 自己パッドだけ**を追加。
  カーネル領域のsha256は `ebd7f523deb59134…` のまま(395a r2以来不変)、
  r2からのコード領域差分 **removed=0 added=31**。パッド確保は
  `if (pad_mb > 0)` の直下にあり、**未設定時は一切確保しない**——静的
  (ガードの直下にあること)と実行時(既定プローブが `[gpu-pad] pad_mb=0` を
  出すこと)の両方でゲートする。r2の配置プローブはそのまま残す。
- Pythonは**一行も変更しない**。Gpは395cのディスパッチャと395cバイナリを
  そのまま使うので、G=133,576.281 を出した経路と完全に同一である。
  sched キャッシュも削除しない(生成コストがセルに混入するため)。

### 事前登録予測(実測前に固定)

1. **P1(表明する予測)**: `S255` は 139,177 の ±0.5% に入る → 因子Aは
   **コンテキスト**である。
   **明示する対立仮説**: `S255` が 133,561 の ±0.5% → 因子Aは**占有量**で
   あり、自プロセスで制御できる。どちらでもなければ因子Aは二択のいずれでも
   なく、r4で再度開く。
   *表明の根拠*: 占有量が効いているなら因子Bと符号が一致するはずだが、実際は
   逆符号である。ただし確信は強くない。
2. **P2**: `S2303 ≥ S255 + 8%` → 因子Bは**所有者を問わない**。
   `|S2303 − S255| ≤ 0.5%` なら因子Bも外部所有者を要する。
3. **P3(表明する予測)**: `X2` は 133,561 の ±0.5% → 因子Aは**1個で飽和**する。
   **対立仮説**: `X2 ≤ 132,225`(D1比 −1%)→ コンテキスト数でスケールする。
   その場合、本番に空のホルダーを1個足すだけの、ほぼ無料の新軸が開く。
4. **P4**: `B512` は 137,080 = 133,561 × (1 + 0.1054 × 512/2048) の ±1.5% →
   因子Bはこの範囲で線形。外れれば勾配に構造があり、細かい掃引の価値がある。
5. **P5(表明する予測)**: Gp実行中、`nvidia-smi` に**2つの**compute
   プロセス——Codonディスパッチャと CRunner——が同時に見え、ディスパッチャ側は
   約250 MiB、すなわち素のコンテキスト以上のものを持たない。`Gp` は 133,576 の
   ±0.5%。
   **反証**: 常に1プロセスしか見えない場合 → G の間に第二コンテキストを
   持つものは存在せず、`D1 == G` は偶然であり、二因子モデルは作り直しになる。
   **本日唯一、その場で現金化しうるセル**: ディスパッチャが250 MiBより
   大幅に多く握っていれば、その超過分は因子Bの勾配上で回収可能な速度である。

### 意味

P1がどちらに転んでも、次の掃引の対象が確定する(自プロセスのパッドか、
ホルダーの構成か)。P3とP5は、外れれば新しい軸が開く側の予測であり、
どちらも追加コストがほぼゼロである。

```
STATIC_ONLY=1 bash 395c_r3_validate.sh   # OK=17(カーネルsha不変、差分0/31、パッドの不活性性 等)
              bash 395c_r3_validate.sh   # CPU等価 → S255 S2303 A0 X2 B512 Gp、約19分
```

**事前条件**: `constellations_N21_6.bin.soa_ref_361.bin.maxd14only_363.bin.sched394f.bin`
と、395cのバイナリ `395c_kernel_maxd14`、ディスパッチャ
`395cPy_kernel_maxd14_final` が存在すること(いずれも395cの実行で生成済み)。
