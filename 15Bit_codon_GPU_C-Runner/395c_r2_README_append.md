## 395c-r2 — 実行順の交絡を潰す(セル順を反転する)

### 395cで確定したこと(再掲)

| セル | 条件 | kernel_ms | vs 基準 |
|---|---|---:|---:|
| D0 | 直接、GPU上に他プロセスなし | 139,188.266 | — |
| D1 | 直接、別プロセスが素のCUDAコンテキスト保持(0 MB) | 133,578.562 | **−4.030%** (vs D0) |
| D2 | 直接、コンテキスト+2,048 MB touch済み保持 | 147,621.453 | **+10.513%** (vs D1) |
| G | `-g 21 21`(ディスパッチャ) | 133,576.281 | **−0.002%** (vs D1) |
| A | 484 | 191,765.484 | — |

全セル `total_sum=314666222712` MATCH。全セル `sm_mean=sm_min=1710 MHz` で
**H_clockは棄却**。GとD1の差は 2.28 ms(0.0017%)で、395a以来の
「ディスパッチャ経由が約4%速い」はコンテキストの存在で**完全に説明された**。

### 395cに残った唯一の穴

セルは `D0 → D1 → D2 → G → A` の固定順で走り、**D0だけがコールドスタート
(30℃)の初回セル**だった。クロックは除外できているが、「セッションの初回
実行は遅い」という説明は395cの設計では排除できていない。もしそれが真なら
H_ctxもH_placeも人工物である。

### 本リビジョンの設計(カーネルは変数ではない)

同じ3条件を**順序を反転して**再測定し、反復を2つ加える。

| セル | 条件 | 395cでの位置 | r2での位置 |
|---|---|---|---|
| **D2r** | ctx + 2,048 MB | 3番目・温間 | **1番目・冷間** |
| D1r | ctx のみ | 2番目 | 2番目 |
| **D0r** | GPU占有なし | **1番目・冷間** | **3番目・温間** |
| D0r2 | GPU占有なし | — | 4番目(直後反復) |
| D1r2 | ctx のみ | — | 5番目(セッション最高温での反復) |

処遇と実行順が最大限に反相関する配置である。ディスパッチャセルは置かない
(395cがGを0.0005%、D1を0.002%で再現済みで、Gは変数ではない。Codonビルドも
不要になる)。

- `395c_r2_kernel_maxd14.cu`: 395cに**ホスト側の診断ブロック1個だけ**を追加。
  カーネル領域のsha256は395c(=395a r2)と一致
  (`ebd7f523deb59134…`)、コード領域差分 **removed=0 added=20**。プローブは
  全 `cudaMalloc` の**後**、`ev_h2d_start` の**前**に置かれ、確保を一切
  行わない(`cudaMemGetInfo` は純粋な問い合わせ)。したがって配置も計測区間も
  変えない——これはハーネスが行番号と確保回数で静的に検証する。
  出力は `[gpu-mem] ld=… results=…` と
  `[gpu-mem-base] ld=0x… ld_off2m=0x… span=… free_mb=…`。
  **D0/D1/D2を時間だけでなくアドレスで区別できるようにするのが目的。**
- ハーネスは各セルの直前に `nvidia-smi --query-compute-apps` で
  **GPU占有を事前条件としてゲート**する(395cのD2は、居残りプロセス1つで
  結果が6%動くことを示した。以後これは観察ではなくゲートである)。

### 事前登録予測(実測前に固定)

1. **P1**: `D0r` と `D0r2` がともに 139,188 の ±0.5% に入る
   → 遅い状態は**初回であること**ではなく**条件**の性質である。
2. **P2(本リビジョン最鋭の検定)**: `D2r` は冷間の初回セルであるにも
   かかわらず 147,621 の ±1.0% に入る
   → 最も遅いセルは、最初に走らせても遅い。
3. **P3**: `D1r ≤ D0r − 3%` かつ `D1r2 ≤ D0r2 − 3%`
   → H_ctxが順序反転下で2回複製される。各セルは 133,579 の ±0.5%。
4. **反証条件**: `D1r` が `D0r` の ±1% に入る、または `D2r` が147,600では
   なく139,000付近に落ちる場合 → 順序・熱が支配的であり、395cのH_ctxと
   H_placeは無効。パディング掃引には進まず、395c-r3で順序問題を再度開く。
5. **副次(閾値なし・証拠のみ)**: `[gpu-mem-base] ld=` の比較。
   - D0rとD1rで**同一アドレス** → 自バッファの配置はD0/D1差の機構では
     **ない**。「別コンテキストが存在すること」自体が別経路で効いている。
   - **異なるアドレス** → 配置説と整合。自己パディング掃引が正しい次手。
6. **副産物**: `|D0r2−D0r|` と `|D1r2−D1r|` が、2:13の実行に対する本
   セッションの真の反復ノイズフロア。394cのセッション間±1.6%はこの数値と
   比較されるべきものである。

### 意味

r2が通れば、395cの−4.03%と+10.51%は処遇の効果として確定し、**配置軸が
探索対象として開く**。通らなければ、4%は未解明に戻り、以後の測定は
すべて初回実行バイアスの疑いを負う。どちらに転んでも、この15分を先に
払わずに掃引へ進むべきではない。

```
STATIC_ONLY=1 bash 395c_r2_validate.sh   # OK=13(カーネル領域sha一致、差分0/20、プローブ非摂動性 等)
              bash 395c_r2_validate.sh   # CPU等価 → D2r D1r D0r D0r2 D1r2、約16分
```

**事前条件**: `constellations_N21_6.bin.soa_ref_361.bin.maxd14only_363.bin.sched394f.bin`
が存在すること(395cのGが再生成済み)。r2はセッション途中でこれを作り直さない
——生成コストが熱状態に混入するため。ハーネスはサイズ(2,025,282×28 B)で
これをゲートする。
