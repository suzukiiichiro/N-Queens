## 395c-r4 — 数か量か、そしてコンテキストは他プロセスでなければならないか

### ここまでの全データ

395c / r2 / r3。全セル `total_sum=314666222712` MATCH、全セル1710 MHz固定。
セッション内反復ノイズ 0.012%、アンカーのセッション間再現 0.007%。

| 総コンテキスト数 | 他プロセス占有 | kernel_ms | A0比 |
|---:|---:|---:|---:|
| 1 | 0 | 139,185.0 | — |
| 2（=本番） | 250 MiB | 133,561.1 | −4.041% |
| **3**（遊休ホルダー2個） | 500 MiB | **133,171.9** | **−4.320%** ← 最速記録 |
| 2（ホルダー1個+512MB） | 762 MiB | 133,854.0 | −3.830% |
| 2（ホルダー1個+2048MB） | 2,298 MiB | 147,634.8 | +6.071% |
| 1（**自プロセス**255 MiB） | 0 | 147,807.0 | +6.195% |
| 1（**自プロセス**2,303 MiB） | 0 | 142,339.5 | +2.266% |
| 本番 `-g 21 21` | 250 MiB | 133,585.2 | −4.023% |

r3は二因子モデルを否定した。他プロセスのメモリと自プロセスのメモリは**符号が
逆**で、どちらも単調でない。S255(`free_mb`=22,017)とD1(`free_mb`=22,018)が
10.7%違うので、**空きメモリは説明変数ではない**。またr3は、Codon親が G の
実行中ずっと正確に250 MiB——素のコンテキストのみ——を保持することを直接
サンプリングで確認した（66/66サンプル）。親から回収できるメモリは無い。

### 本リビジョンが答える2つの問い

1. **X2（ホルダー2個・500 MiB・3ctx）は B512（ホルダー1個・762 MiB・2ctx）
   より速かった。数のせいか、量のせいか。**
   `Y510` はホルダー1個に255 MBを確保させ、**X2bと同じ510 MiB**を占有する
   （コンテキスト255 MiB + 確保255 MiB）。`free_mb` は1 MiB以内で一致し、
   **違うのはコンテキスト数だけ**になる。
2. **追加コンテキストは他プロセスでなければならないか。**
   `NQ_EXTRA_CTX` は自プロセス内で `cuCtxCreate` により遊休コンテキストを
   作り、直ちに `cuCtxPopCurrent` でスレッドから外す。以降のランタイムAPIは
   従来どおりプライマリコンテキスト上で動く。これで効果が再現すれば、
   **本番はヘルパープロセスを一切必要としない。**

### セル（順序は変数ではない——r2が決着させた）

| セル | 構成 | 総ctx | 他プロセス占有 |
|---|---|---:|---:|
| **X2b** | ホルダー2個 × 0 MB（記録の複製） | 3 | 510 MiB |
| **Y510** | ホルダー1個 × 255 MB | 2 | 510 MiB |
| **M1** | `NQ_EXTRA_CTX=1`、ホルダーなし | 2 | 0 |
| X4 | ホルダー4個 × 0 MB | 5 | 1,020 MiB |
| B1024 | ホルダー1個 × 1024 MB | 2 | 1,279 MiB |
| X6 | ホルダー6個 × 0 MB | 7 | 1,530 MiB |

- `395c_r4_kernel_maxd14.cu`: r3に **`NQ_EXTRA_CTX` だけ**を追加。カーネル
  領域のsha256は `ebd7f523deb59134…` のまま（395a r2以来不変）、r3からの
  コード領域差分 **removed=0 added=55**。ドライバAPIを使うため
  **リンクに `-lcuda` が要る**（`#include <cuda.h>` は `#ifdef __CUDACC__`
  の内側にあるので、gccのCPUテストビルドは影響を受けない）。
  未設定時は何も作らず、静的（`if (want > 0)` ガード）と実行時
  （既定プローブが `[gpu-ctx] extra_ctx=0`）の両方でゲートする。
  さらに `NQ_EXTRA_CTX=1` の短縮プローブを本番セルの前に走らせ、
  `cuCtxCreate` が実際に通ることを19分を費やす前に確認する。
- **本リビジョンは本番を変更しない。** Q2が「数」、Q3が「他プロセス」と
  出た場合、r5でディスパッチャにホルダーを組み込み `-g` を実測する。

### 事前登録予測（実測前に固定）

1. **Q1**: `X2b` は 133,172 の ±0.1% に入る。反復ノイズが0.012%なので、
   0.1%はその8倍。**再現しなければ記録ではなかった**ということであり、
   以下すべてはその前提で読む。
2. **Q2（表明する予測）**: `Y510 ≥ X2b + 0.25%` → 軸は**コンテキスト数**。
   *根拠*: 量だけの曲線なら、250 MiBで133,561、762 MiBで133,854だから、
   510 MiBは約133,70xに内挿されるはずで、X2bの133,172よりはるかに遅い。
   **対立仮説**: `|Y510 − X2b| ≤ 0.1%` → 軸は**量**であり、500 MiB付近に
   最適点がある。その場合、X4とX6は情報を持たない。
3. **Q3（表明する予測）**: `M1` は 139,180 の ±0.5% → 自プロセス内の
   コンテキストでは何も起きず、追加コンテキストは**他プロセス**でなければ
   ならない。*根拠*: 自プロセスのメモリパッドが他プロセスと逆符号だった
   という先例。
   **対立仮説（そしてこちらが価値のある側）**: `M1 ≤ 133,600` →
   効果はプロセスではなく**デバイス上のコンテキスト**の話であり、本番は
   環境変数ひとつで、ヘルパープロセスなしにこれを得る。`NQ_EXTRA_CTX` が
   そのまま本番のつまみになり、残る軸のうち最も安いものになる。
4. **Q4**: `X4 ≤ X2b` かつ `X6 ≤ X4`、各段の改善幅は前段より小さい。
   **反証**: `X4 > X2b` なら、1,020 MiBの時点でメモリ罰則が既に勝っており、
   数の軸は3コンテキストで頭打ち。
5. **Q5**: `B1024` は 134,000〜140,000 に入る → 2,298 MiBで見えた+10.5%は
   1,279 MiBではまだ始まっていない。`B1024 ≥ 145,000` なら崖は1,279 MiBより
   下にあり、本番は意図的にその下に留まらねばならない。恒久的な設計制約として
   記録する。

### 併せて記録すべき制約

r3で判明した通り、**CRunnerが自分でデバイスメモリを確保すると重い罰則が
つく**（255 MiBで+6.2%、2,303 MiBで+2.3%）。**N=22/23のmaxd16は今より
大幅に多くのデバイスメモリを要求する**ので、N=22の作業に入る前にこのコストを
実測しておく必要がある。

```
STATIC_ONLY=1 bash 395c_r4_validate.sh   # OK=17（カーネルsha不変、差分0/55、cuCtxPopCurrentの存在 等）
              bash 395c_r4_validate.sh   # CPU等価 → X2b Y510 M1 X4 B1024 X6、約19分
```

**事前条件**: sched入力が存在すること。`-lcuda` のリンクが通らない場合は
`-L/usr/lib/x86_64-linux-gnu` を足す（ハーネスの失敗メッセージにも記載）。
