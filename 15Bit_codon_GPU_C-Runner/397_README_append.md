### 397が検証する仮説はひとつだけ

L1圧の説明候補は2つ残っている。

- **(a) 量** — push/popで動くローカルメモリのバイト数
- **(b) 発散** — スレッドごとにスタック深さが違い、ワープ内でアドレスが
  散ってセクタが割れる。バイト数が小さくてもL1トラフィックは増える

397は**(a)だけ**を叩く。

```
word A (uint64_t): ld(21) | rd(21)<<21 | col(21)<<42     = 63ビット
word B (uint32_t): avail | depth<<27                     = 現行のまま
```

16 B → 12 B。**そしてローカルアクセス回数は push 2回 / pop 2回 のまま。**
リクエスト数と発散は不変なので、(a)と(b)が交絡しません。3ワードに分ければ
バイト数は減ってもアクセスが3回になり、遅くなったとき原因が分からなくなる。
そこを避けた設計です。セクタ数は push/pop それぞれ 16 → 12。

### 通常より厳しくゲートする理由

この詰め方は **ld と rd の 2^21 以上のビットを push 時に落とします**。
「全使用箇所が board_mask で覆っているので N≤21 では死にビット」という
のが根拠ですが、**これは推論であり、この案件は推論を信用せずゲートします。**

したがって**タイミングを1つも読む前に**、両バイナリでフル入力
（2,025,282レコード）を走らせ、per-recordの出力を**バイト単位で比較**します。
一致しなければハーネスは停止し、数値は一切報告しません。

### 事前登録予測（実測前に固定）

1. **V1**: ptxasのスタックフレームが 208 → **140〜168 B**、spill 0/0、
   レジスタ 42本以下。**外れたら詰め替えが効いていないので、GPU時間を
   使う前に停止。**
2. **V2（ハードゲート）**: フル入力での per-record 出力がバイト一致し、
   両者 `total_sum=314666222712` MATCH。
   **落ちたら「2^21以上は死にビット」という推論が誤りで、時間は読まない。**
3. **V3**: (a)が正しければ `Gn ≤ Gb − 1.0%`。
   **私の表明する予測は `|Gn − Gb| ≤ 0.3%`、すなわち(a)は棄却される。**
   根拠は 320スレッド/SM × 208 B = 66.6 KB で L1 128 KB に収まっており、
   容量が溢れているとは考えにくいこと。**確信は強くありません。**
   だからこそ走らせる価値があります——どちらに転んでも398の行き先が決まる。
4. **V4**: 直接実行 + `NQ_EXTRA_CTX=2`（3コンテキスト、`free_mb` 21763）が
   **133,18x の ±0.15%** に入る。ディスパッチャなしで本番状態を再現できる
   ことの確認で、以後の測定が1回2.5分短くなります。

### 記録すべき限界 — 意図的に残す

21ビット×3で64ビットの63を使い切るので、**この詰め方は N≤21 専用**です。
`main()` は N>21 を拒否します（両方の main にガードを入れ、ハーネスが
N=22で実際に拒否されることを実行時に確認します）。

**N=22/23 の maxd16 には別のレイアウトが要ります。397は実験であって、
勝ってもそのまま将来へ持ち越せる形ではありません。**
