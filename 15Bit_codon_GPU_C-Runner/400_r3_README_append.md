## 400-r3 — L1/共有メモリのカーブアウト

### まず訂正 — 396〜399のノートに誤りがあります

私は繰り返しこう書きました。

> 「394fは79ラウンド全体でスレッドごとの累積負荷を揃えている」

**検証しないまま述べた推論で、誤りです。** `394f_permute_soa7.py` の `sched` モードは

```
stable sort by (markctrl, ctrl0): schedule similarity
```

であり、**strideという概念もなく、負荷均衡もしていません。**

394fが実際に買っているのは**ワープ内同質性**です。ワープを共有する32レコードは
ファイル上で連続しており、制御ワードが同一か隣接なのでレーンが同じ経路を辿ります。
399で測った「shuffleで35.2%遅化、レーン稼働率10.53→6.78」は、まさにこれでした。

**396-r2 / 398 / 399 の該当記述は、この訂正で置き換えてください。**

### 400-r2の実測 — オカパンシーを上げると6〜7倍遅い

| stride | k/thr | warps/SM | mean ms | base比 |
|---:|---:|---:|---:|---:|
| 25,600 | 35.0 | 10 | 2,120.2 | — |
| 40,960 | 21.9 | 16 | 3,849.1 | +82% |
| 81,920 | 11.0 | 32 | 10,699.4 | +405% |
| 122,880 | 7.3 | 48 | 16,241.9 | +666% |

**各strideでBLOCK違いは1%以内で一致。効いているのはstride（常駐スレッド数）で
あって、ブロック形状ではありません。** Z2も成立（stride固定なら BLOCK=64 が
−1.07%、BLOCK=128 が +6.54%）。

### 犯人は作業集合、という推定

ワープ内同質性は「連続32個」という性質なのでstrideに依りません。**大strideで
壊れるものではない。** strideとともに変わるのは常駐スレッド数、すなわち
ローカルメモリ作業集合です。

```
L1=128 KB なら 106.5 KB は収まるはず。だが実測は既に +82%
L1= 64 KB なら 66.6 / 106.5 / 213.0 KB = 1.04 / 1.66 / 3.33 倍超過 → 曲線に合う
```

**既定のカーブアウトが共有メモリ側にかなり割いている疑いが強い。**
このカーネルは `__shared__` も `__syncthreads` も使いません（ptxas
`used 0 barriers`）。**共有に割かれたバイトは丸ごと無駄です。**

### r3が変えるもの — ホスト側2つ

1. **`NQ_CARVEOUT`（0〜100）**。未設定なら属性に一切触れないので400-r2とビット同一。
   0は共有最小＝L1最大。
2. **`cudaFuncGetAttributes` を毎回呼び**、`[gpu-carveout]` 行に
   `effective_pref` / `local_bytes_per_thread` / `static_shared_bytes` /
   `registers` を出力。

> **既定のカーブアウト値も、1スレッドあたりローカルメモリ量も、タイミングを
> 読む前にログで分かります。**

`.cu` のコード領域差分は **removed=0 added=46**、カーネル領域sha `ebd7f523…` 不変。

### 事前登録予測（実測前に固定）

1. **K1**: カーネル領域sha `ebd7f523`、ptxas 37レジスタ/208Bフレーム、
   `NQ_CARVEOUT` 未設定なら `requested=-1`。
2. **K2**: `local_bytes_per_thread = 208`、`static_shared_bytes = 0`、
   `registers = 37`。**ここが違えば本リビジョンの容量計算は全部やり直し。**
3. **K3**: **表明する予測——既定の `effective_pref` は 0 ではない。**
   0なら既定で既にL1最大ということで、K4は空振りします。
4. **K4**: **表明する予測——stride 81,920 で `NQ_CARVEOUT=0` は既定より
   10%以上速い。** 2%以内なら「カーブアウトは既にL1最大」で、容量は
   **フレーム縮小でしか叩けない**ことになります（397の着想を正しくやり直す根拠）。
5. **K5**: ローカルメモリのL1ヒット率は stride とともに落ち、`NQ_CARVEOUT=0`
   で上がる。**これが容量説の直接検定です。** 落ちなければ、6〜7倍は容量効果では
   なく別の機構です。
6. **K6**: stride 25,600（現行本番）ではカーブアウトの効果は1%以内。
   66.6 KB は既定L1にも収まっているはずだから。**ここが動くなら容量モデルが
   間違っています。**

### 掃引

r2で「ブロック形状はほぼ中立」と分かったので、**strideごとに代表1構成**に絞り、
カーブアウト2値と掛けます。

| stride | 構成 | warps/SM |
|---:|---|---:|
| 25,600 | 32×800 | 10 |
| 40,960 | 64×640 | 16 |
| 81,920 | 64×1280 | 32 |
| 122,880 | 128×960 | 48 |

4 stride × 2カーブアウト × 3反復、N=19で約4分。ncuのL1診断が4本で約5分。
確認はN=20。**通しで約15分**です。

### ハーネスの修正

r2のTSVには **N列とcarveout列が無く**、N=19の掃引とN=20の確認が同じ行に
マージされて `spread 154%` という異常値を出しました。r3で両方の列を追加し、
ログファイル名にもカーブアウトを含めました。

```
STATIC_ONLY=1 bash 400_r3_validate.sh   # OK=19
              bash 400_r3_validate.sh   # 約15分
NPROF=20 NCONF=21 NBIG=22 bash 400_r3_validate.sh   # 本番規模
```
