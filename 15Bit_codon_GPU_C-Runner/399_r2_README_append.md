## 399-r2 — 失った測定を取り戻し、軸に値札を付ける

### 399が決着させたこと — 並び順は35.2%効く

N=20、各3反復、全12走行オラクル一致（置換不変性は成立）。

| 順序 | 平均 kernel_ms | 反復幅 | 394f比 |
|---|---:|---:|---:|
| **asis（394f）** | **16,482.743** | 0.020% | — |
| desc | 16,548.483 | 0.014% | +0.399% |
| asc | 17,054.993 | 0.041% | +3.472% |
| **無作為shuffle** | **22,285.509** | 0.010% | **+35.205%** |

> **レコードの並び順は35.2%の価値を持つ。394fは無作為に対して26.0%を稼いでいる。**

事前登録の閾値は2%でしたから、桁違いに超えました。**X3成立、軸は生きています。**
X4も表明どおりで、私のproxyソートは394fに勝てませんでした。

フェーズBがその理由を示しています。32レコード組の内部で `w_lo` の分散は全体の
**8.2%**——**394fは既にスケジュールワードでワープ内を揃えています**。
なお `popcount(col)` は全体分散がゼロでした。全レコードで配置済みクイーン数が
同じなので、**proxyとして無意味**です。

r2で復元し、398-r2で動いた形をそのまま戻しました。

### 失った測定の価値は、むしろ上がりました

35.2%の振れは**較正点**になります。398-r2は394f順で
`Avg Active Threads Per Warp = 10.53/32` を測っています。時間がレーン稼働率に
反比例するなら、shuffle順は

```
10.53 × 16,482.7 / 22,285.5 = 7.79 / 32
```

を示すはずです。**測れば軸に傾きが付きます**——「生きレーンが1本増えると何%
速いか」。この数字がなければ「レーン稼働率32.9%」は**値札のない診断**にすぎません。

### 推測ではなく実測のコストproxy

399のソートは `popcount(free)` という**推測**でした。

`stride ≥ records`（N=20なら `NQ_MAX_BLOCKS=42784`）にすると**1スレッド1
レコード**になり、出力ファイルはスレッド合計ではなく**レコードごとの解数**に
なります。これは実測量です。

しかもこれでソートすると、ランク r はスレッド `r mod stride` に載るので、

- **各スレッドが全ランク帯から1つずつ受け取る**（負荷均衡）
- **各ワープが隣接32ランクを持つ**（ワープ内同質性）

が**同時に**成り立ちます。

### 事前登録予測（実測前に固定）

1. **Y1**: ストール理由の首位は **long_scoreboard 系で25%以上**（X1の再掲、
   3度目）。分岐解決が首位なら、レーン稼働率の解釈をやり直します。
2. **Y2**: shuffle順の `Avg Active Threads Per Warp` は **7.0〜8.6 / 32**
   （反比例仮定からの点予測 **7.79**）。**外れれば時間とレーン稼働率は単純
   比例ではなく、軸の値札付けはやり直しです。**
3. **Y3**: desc順の稼働率は shuffle と asis の**あいだ**にあり、時間と単調に
   対応する。
4. **Y4**: **表明する予測——実測コストソートは394fの ±1% 以内。**
   1%以上速ければ、**この軸から得た最初の実利**になります。
5. **Y5**: 新しい順序すべてで `total_sum = 39,029,188,884`。ハードゲート。
