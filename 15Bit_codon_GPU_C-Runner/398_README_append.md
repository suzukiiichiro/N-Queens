## 398 — 作らずに測る。N=20 / N=19 でストール内訳とローカルメモリを取る

### 397は破棄

397はDFSスタックを16→12バイトに詰め替えた。ptxasでは **208 → 160バイト**、
spill増なし（レジスタ 37 → 38）で、詰め替え自体は効いていた。しかし
**等価性ゲートが、タイミングを1つも読む前に棄却**した。

```
396_r2  total_sum = 314,666,222,712   MATCH
397     total_sum = 427,786,151,034   ← 解が多すぎる
```

理由は構造的で、記録に値する。**`cur_ld` の全使用は左シフト、`cur_rd` の
全使用は右シフト**である。

```
cur_ld : 611, 614, 733, 747   すべて <<
cur_rd : 612, 615, 734, 748   すべて >>
```

ld の board_mask 超のビットは上へ逃げ、全使用箇所が `bm` で覆うので死んで
いる。しかし **rd の上位ビットは、探索が深くなるにつれて降りてきて制約
として効く**。rdをマスクすれば制約が落ちる。解が増えたのはこのためである。

真の必要幅を積むと **ld 20 / rd 32 / col 21 / avail 21 / depth 4 = 98ビット**。
12バイトは96ビット。**2ビット足りない。** 詰め替えで量仮説を検証する道は
塞がっており、398はこれを追わない。

**397は診断が終わる前に手を動かした。本案件が普段避けている過ちである。**

### 訂正 — N=22 は maxd14 で動く

397のノートに「N=22/23はmaxd16が要る」と書いたが**誤り**だった。
`select_static_maxd()` は `required_maxd <= 14` なら 14 を返し、rev372の
記述によれば **N=22 も `required_maxd=14`（366で3/3確認）**。

**N=22はこのカーネルで動く。** N=23は未検証。したがって「Nを21で頭打ちに
する詰め方」は、遠い将来ではなく**次の目標そのもの**を塞ぐ。

### 398が答える2つの問い

- **U5**: 支配的なwarpストール理由。**一度も答えが出ていない。** 396は
  フル N=21 で WarpStateStats を2回試し、2回ともncuがエラーで落ちた。
  ただし**1.5秒の入力では成功している**ので、原因は権限ではなくカーネル長。
- **(a)量 vs (b)発散**: これが「詰め替え作業に価値があるか」そのものを決める。

### なぜ N=20 / N=19 か

レコード部分集合は使えない。396と396-r2の実測で、切り詰めは
レコードあたり13〜26%安く、層化は12〜37%高く出た。**394fは79ラウンド
全体でスレッドごとの累積負荷を揃えており、部分集合を取ると均衡が壊れる**
（単独ラウンドはフル実行の中にいるときの1.74倍かかる）。

N=20 と N=19 は**それぞれ自前の394fスケジュールを持つので構成上バランス
しています**。N=20は約16秒、N=19は約2秒。ncuが動くと実測された範囲です。

**代表性は仮定しません。** N=21の Occupancy と Scheduler Statistics は396で
実測済みなので、W6で直接突き合わせます。

### 事前登録予測（実測前に固定）

1. **W1**: アンカー（直接実行 + `NQ_EXTRA_CTX=2`）が 133,185 の ±0.15%。
   397で **V4が成立済み**（E0 = 133,155.344、−0.022%）なので、
   **ディスパッチャなしで本番状態を再現できます**。1回2.5分の節約。
2. **W2**: N=20 の `kernel_ms` が 14,000〜20,000、N=19 が 1,500〜3,000。
   情報用（ハードゲートにしない）。
3. **W3**: N=20 の支配的warpストール理由は**分岐解決系で25%以上**。
   **反証されれば律速要因は移動しており、399は最適化ファミリを変える。**
4. **W4**: ローカルメモリの **sectors/request**。
   **表明する予測: ≥ 2、すなわち(b)発散が支配的。**
   根拠は、ローカルメモリがスレッド間インタリーブ配置であること——ワープ内
   の全レーンが同じワード添字を触れば完全合体しますが、DFSの深さがレーン
   ごとに違えば添字が散ってセクタが割れます。**深さの発散はこのアルゴリズム
   に内在します。**
   **≤ 1.2 なら(b)は棄却**され、量が効いていることになる。**そのときに限り**、
   98ビットを96に収める工夫に価値が出ます。
5. **W5**: N=19 と N=20 で、ストール理由の**上位3件の順序が一致**する。
   一致すればN=21の答えとして採用。しなければ順位はN依存で、N=21そのものを
   夜間に回す判断になります。
6. **W6（代表性の直接検証）**: N=20 の達成オカパンシーが **10.32% ±3ポイント**、
   No Eligible が **61.63% ±5ポイント**以内。N=21で実測済みの値との突き合わせ
   なので、これは仮定ではなく検証です。

### 段取りと所要

| 段階 | 内容 | 目安 |
|---|---|---|
| 0 | 静的ゲート、ビルド | 3分 |
| 1 | **ncu権限プローブ**（高価な処理の前） | 3秒 |
| 2 | W1 アンカー（直接実行） | 2.2分 |
| 3 | W2 `-g 20 20` / `-g 19 19` で入力生成＋ベースライン計測 | 数分 |
| 4 | プロファイル（N=20 → N=19、各4パス） | 予算30分 |

各パスは `WarpStateStats` →ローカルメモリ専用メトリクス→
`MemoryWorkloadAnalysis` → `SpeedOfLight`+`Occupancy`+`SchedulerStats` の順。
**U5に直結する WarpStateStats を必ず先頭**に置きます。セクションごとに
600秒のタイムアウト、全体予算1800秒。

入力ファイル名は推測せず、**CRunnerログの `src=` から読み取ります**。

```
STATIC_ONLY=1 bash 398_validate.sh   # OK=16
              bash 398_validate.sh   # 約35分
NCU_PREFIX=sudo bash 398_validate.sh # ncu呼び出しだけを昇格
```

**ハーネス全体をsudoで走らせないでください。** ncu呼び出しのみ昇格し、
出力は `reclaim` で所有者を戻します。

### 四点の同一性

- `398_kernel_maxd14.cu`: 396-r2のリネーム。コード領域全体 sha256
  `c5dbde3f1002229b…` が一致し、**カーネル領域は395a r2の
  `ebd7f523deb59134…` に戻っています**。397の詰め替えが残っていないことも
  静的にゲートします。
- `398Py_kernel_maxd14_final.py`: 396-r2Pyからの差分は**実行行3行**。
  `env_prefix="NQ_EXTRA_CTX=1 "` は維持。

### 397から拾えるもの

破棄はしますが、3つ残ります。**フレームは実際に208→160まで縮む**こと、
**ldとrdの構造的非対称性**（左シフト/右シフト）、そして **V4の確立**
（`NQ_EXTRA_CTX=2` の直接実行で本番状態が再現でき、以後の測定が
1回2.5分短くなる）。
