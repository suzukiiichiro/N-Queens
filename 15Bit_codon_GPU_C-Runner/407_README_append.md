406の結果と採用は `406_results_README_append.md` に記録済み（N=21 100,714 ms／N=22 879,437 ms）。

### 静的読み：406と405の突き合わせ（`<403>`、マークなし、GPUゼロ）

406で変わったのは、状態の退避のMOVが消えたこと、future_checkが分岐1本になったこと（405は「深さのフラグで分岐→
計算→分岐」の2段でBSSY領域とBREAKがあった）、pushガード周りのBREAKが1本減ったこと。
どの数も−5.9%を説明しない。静的には内訳を分けられなかった → 診断セルのKで分けた（下）。

読み：

- **Kが406の−5.9%の内訳を分けた。** Kは406の `nf` の経路を残したまま、MOVとBREAKだけが戻った形で、9.2%遅い
  （405より2.8%遅い）。406の利得は「分岐の深さ」だけではなく、**MOV／制御の形**から来ていた。
  候補3（future_checkと `cur_x` の共通化）は、この綴りでは閉じる。
- **MとM2はループ長（112）もマークの腕（14命令）も同じで、2.3%違う。** ループ長では順序が付かない。
  レジスタ55本のMのほうが速かったので、「レジスタ≤44」のゲートが時間に効いているという証拠は今回は無い
  （ゲートは変えない）。M系はこのままでは進めない。
- J+M2（−0.82%）はJ（−1.44%）より悪い。足し算にならない、を再確認。
- 事前登録どおり、次のリビジョンは測ったセル1つ＝**J**。
- N=21の直接実行が初めて100秒を切った（D1 99.1秒）。

### 407の変更

```
uint32_t child_jmark = (child_jmark_mask >> cur_depth) & 1u;
if (child_jmark != 0u) {            →   nf &= ~child_jmark;
    nf &= ~1u;                           if (nf == 0u) {
    if (nf == 0u) {                          continue;
        continue;                        }
    }                                    nld |= child_jmark;
    nld |= 1u;
}
```

`child_jmark` が0なら `nf` も `nld` も変わらず、`nf` はすでに非ゼロなので、どの経路でも値は同じ。
ほかは不変（`nf` の2つの腕、`cur_x`、future_check、マークの腕、push／pop、ルート経路）。

- `.cu`：406比 コード領域 **removed=6 added=4**。406に生成器（J）を適用した結果とバイト一致。kernel sha `0cc7876f`。
- `.py`：406Py（本番）の純粋リネーム、実行行3行。
- ハーネス：`407_validate.sh`。

### 恒久ルール（追加）

- 静的に内訳を分けられないときは、「片方の要因だけを戻した変種」を診断セルに載せて分ける（407のK）。
  負けると分かっている変種でも、2分で要因が分かるなら測る。
- 状態を持ち越す変数を増やす綴り（`nx` のように複数の経路で書き換えるもの）は、退避のMOVを呼び戻しうる。
  探索でMOVの本数が増えた変種は、命令数が減っていても候補にしない。
- 未探索の変種を診断に載せるときは、160 B・spill 0とCPU等価を先に確認し、shaを記録する（407のD4・D5）。

### この先

- **分岐領域をまとめる方向の続き**：Jで効いたので、残るBSSY領域（マークの腕、pushガード）を同じ目で読む。
  pushガードは閉鎖済みの軸だが、406以降は周りの形が変わっている。再検定の対象にしてよい。
- M系：マークの判定が `(7 << 4d) & schedule64` の5命令になっていた（ニブルを使わなくなったため）。
  ニブルの抽出を残す綴りにすれば、マークなしの経路を406と同じに保てる可能性がある。探索から。
- Kの別綴り：`nx` を使わず、降下時に `cur_x` を1命令で作れる形があるかは未確認。
