## 394f — 生順序は「隣接が似ているから」良いのか(順序プローブ)

**カーネル・Codon側とも機能変更なし。** `394f_kernel_maxd14.cu`は394eの
ヘッダーのみリネーム、`394fPy`は純粋リネーム。測定は
`394f_permute_soa7.py`で生の入力ファイルの順列を作り、
`394f_run_order_probe.sh`がC版バイナリを直接叩く(484×32、sudo不要)。

### 動機(394e)

罰がwarp内(M1)と確定し、機構は「broadmarktailのレコード単位
インターリーブが重いレコードを全warpに散らす」ことにあると読めた。
裏返せば、**生順序が良いのは隣接コンステレーションが似ているから**、
という仮説になる。これが正しければ(a)ランダムシャッフルはbaseと同じ
くらい悪く、(b)似たものをより強く集める並びは生を上回りうる。

### 順列(すべて生からの順列、ツールが順序非依存チェックサムで確認)

| セル | 内容 | 位置づけ |
|---|---|---|
| R | 生 | アンカー |
| **X** | **ランダムシャッフル**(seed=394) | **対照**。隣接性が要因なら+30〜50% |
| L1 | `(col, ld, rd)`で安定ソート | ルート状態の類似 |
| L2 | `(−popcount(free), col, ld, rd)` | コスト代理(空き数)を先に |
| L3 | `(markctrl, ctrl0)`で安定ソート | スケジュール類似。同キー内は生の隣接を保つ=**インターリーブなしのfuncidグルーピング** |

各セルN=21フル、オラクルゲート。C版の`results[tid]`(per-thread解数)を
回収し、max/mean・CV(%)をスレッド間均衡の代理として記録する。
約20分。

### 事前登録予測(実測前に固定)

1. Rは201,237を±1%で再現。
2. **X ≥ +30%。** 反証条件: Xが±5%以内なら「隣接性」は要因ではなく、
   broadmarktailのインターリーブは別の固有の理由で悪い。
3. **L1 ≤ R −3%**(主予測)。反証条件: L1 ≥ Rなら、生成器の順序は構造
   ソートで超えられない(生が実質最適)。
4. L3 ≤ R。funcidグルーピング自体は無害か有益で、悪いのは
   インターリーブだけ、という394eの読みの直接検証。
5. L2はL1とRの間。
6. スレッド間代理(CV)はX・L1〜L3とも生と大差なし(M1の話なので)。

### 394fの後

- X大・L1小(仮説どおり)なら: 「似たもの同士のwarp」を最大化する並びを
  395系の正式な軸にする。次はchunkshape148の**スコアキーそのもの**で
  グローバルにソートした並び(Dの−1.0%の再現・強化)を、394b r3の
  最適MAX_BLOCKSと組み合わせる。
- X小なら: 隣接性は要因でなく、インターリーブ固有の問題。並べ替え軸を
  本番C経路についてクローズし、395a(`nibble_op`二重計算除去)へ。

### 何が分かったか

**隣接性が要因である。** ランダム順(+44.2%)はbroadmarktail base(+47.5%)と
同等——baseの罰は「隣接性の破壊」でほぼ全額説明でき、それ以上の固有の
悪さはない。

**ただし「隣接」の中身はルート状態の数値的近さではない。** `(col,ld,rd)`
ソートは+20.8%、空き数優先でも+21.2%。生成器の順序が同じwarpに置いて
いるのは(i,j,k)を共有する**兄弟コンステレーション**——ほぼ同型の部分木
——であり、ビットマスクの辞書順はそれを散らしてしまう。生の価値の
約半分はマスク類似で回収でき、残り半分は兄弟性そのものにある。

**スケジュール同質性は独立した小さな利得。** L3は生の隣接ペアを99.4%
保持したまま(markctrl, ctrl0)の同じクラスを固め、−1.71%。broadmarktail
の狙い(funcidグルーピング)自体は正しく、**インターリーブがそれを台無し
にしていた**という394eの読みが確定した。

**warp間の均衡は無関係であることの決定的な証拠。** per-warp解数の
CVはランダム順が**最も均衡**(1.26%、生5.35%)でありながら44%遅い。
C版カーネルの外側`BSYNC B4`(毎周回のレーン再収束)にとって、
warp内の32レーンがロックステップで進めるかどうかがすべてである。

### 結論・採用方針

- broadmarktail→chunkshape148の並べ替えは本番C経路について**不採用で
  クローズ**。
- **L3(スケジュール安定ソート)を採用候補にする**(−1.71%、コード変更
  ゼロ、`394f_permute_soa7.py sched`の1段をCRunner入力パイプラインの
  4段目に加えるだけ)。394gで`MAX_BLOCKS`最適点との合成を確認してから。
- 順序軸の残る上振れは「兄弟性を保ったままコスト均質化する並び」だが、
  兄弟グループは32未満で、生成器の順序が既に事実上それを実現している。
  この軸は**L3で一段落**とし、以後はカーネル側(395a〜c)へ重心を移す。
