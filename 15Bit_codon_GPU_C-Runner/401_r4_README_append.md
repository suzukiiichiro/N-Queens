## 401-r4 — 状態は外部ホルダーで作る。r3が読めなかったものを測り直す

### 401-r3の結果（2026-09-28）

全11走行オラクル一致、GPU空きゲート全通過、ホルダー以外の居残りなし。

**R5は成立**（ホルダーはディスパッチャ側に付いた）。**R1（ハードゲート）は落ちた。**
D21_m800の139,181は、395cのD0（他プロセスなし＝1コンテキスト、139,188）と
0.005%で一致する。ログには `extra_ctx=2`・`free_mb=21762` と出ているのに、
性能上は「コンテキスト1個」として振る舞った。クロック低下なら別の数字になる。

9/9のログと突き合わせると、9/9午前（395c-r4 M1=D1、r6 A/B）は自プロセスctxが
効いており、9/9 22:33以降の401-r2自身の `-g 21 21`（133,555.8）と同夜のN=20
Dx2（17,378）は今日と同値。**9/9夕方のどこかで、自プロセス内 `cuCtxCreate` の
コンテキストが「数えられなく」なった**——これが最も整合的な読みだが、原因は不明で
**仮説として記す**。他プロセスのコンテキスト（Codon親、ホルダー）は9/9も今日も
0.01%で再現している。ドライバ 595.91.07・カーネル・Persistence-M は同一。

帰結として **r6の413 msは現状態では出ていない**。`-g 21 21` の実測は133,56x
（2コンテキストの値）で、本番の期待値は当面 **133,56x** と読む。

r3のN=21梯子（720 +5.15% / 880 +9.38% / 1280 +84.56%）は1ctx状態で測ったもので、
**事前登録上は読まない**。参考値に留める。

### 恒久ルール候補（本リビジョンで採用判定）

> **直接実行の測定は、`NQ_EXTRA_CTX` ではなく外部ホルダー（`395c_ctx_holder`）で
> GPU状態を作る。** 自プロセス内コンテキストは効いたり効かなかったりするが、他
> プロセスのコンテキストは0.01%で再現する。

### 事前登録予測（実測前に固定）

1. **P0**: G21 が 133,567 の ±0.15%（r3の値＝今日の本番状態）、`extra_ctx=1`、
   `free_mb=21,762`。
2. **P1（ハードゲート）**: H0 が 133,561 の ±0.15%（395c-r4 D1＝2ctx）、
   `free_mb=22,018±2`、`extra_ctx=0`。**落ちたらホルダー方式も状態を再現しておらず、
   以下はすべて読まない。**
3. **P2（表明する予測）**: |H1 − H0| ≤ 0.10% —— 自プロセスのコンテキストは今は
   何も足さない。**対立仮説**: H1 ≤ H0 − 0.25% → 再び数えられており、効果は時間
   変動する（その場合、r3のD21異常も時間変動であり、状態の監視が恒久的に要る）。
4. **P3（表明する予測、確信は弱い）**: H2 ≤ H0 − 0.25%（約133,18x〜133,20x、
   395c-r4 X2b相当）—— 切り欠きは存在するが、本物の第3コンテキストが要る。
   **反証**: H2 が H0 の 0.10% 以内 → 切り欠きは消えており、本番の値は133,56xで
   確定。成立した場合、本番がホルダー（補助プロセス）で413 msを取り戻せるかは
   別リビジョンで交互A/Bにかける。**1回の実測では採用しない。**
5. **P4**: L1280 ≥ H0 + 20%。401-r2のM3/M4を正しい状態で閉じる。
6. **P5（表明する予測）**: L720 は L800 より +1.5〜+6% 遅い（394gの8→10段が
   −4.6%、r3の参考値が+5.15%）。**反証**: ±0.3%以内か速い → L1内の傾きは寝ており、
   402は書く前に計画し直す。
7. **P6（表明する予測）**: L880 は L800 より遅い（r3の参考値+9.38%）。成立なら
   実効L1予算は65 KB側で見積もる（104バイトなら20 w/SM）。0.3%超で速ければA/B
   候補として記録のみ。
8. **P7**: |L800 − H0| ≤ 0.05%（同一状態の複製＝本セッションのノイズフロア）。
9. **P8**: 全セルの平均SMクロックが1710の±2%。外れたセルはクロック効果が混入
   しているので、そのセルの値は読まない。

### 本リビジョンが変えないもの

本番既定は変えない。`env_prefix` の `NQ_EXTRA_CTX=1` は害が無いので残す。P2が
成立すれば「記録のため残す（性能上は不活性）」へ格下げし、README本文の本番値を
133,56xに改める。

### 四点の同一性

- `401_r4_kernel_maxd14.cu`: 401-r3のリネーム。最初の `#include` 以降は**バイト一致**
  （コード領域全体 `f1a03a7fed723c55…`、カーネル領域 `ebd7f523deb59134…`）。
- `401_r4Py_kernel_maxd14_final.py`: 401-r3Pyからの差分は**実行行3行**。
  `env_prefix="NQ_EXTRA_CTX=1 "`、`CRUNNER_MIN_N=19` は維持。r4のノートを `#`
  ブロックとして先頭に追加。
- `401_r4_validate.sh`: 新規。ホルダー複数本の制御、PID許可リスト式のGPU空き
  ゲート、セルごとのクロック採取、P0〜P8の判定。

```

              bash 401_r4_validate.sh                 # 約24分
CELLS="G21 H0 H1 H2" bash 401_r4_validate.sh          # 状態プローブのみ（約10分）
CELLS="H0 L720 L800 L880 L1280" bash 401_r4_validate.sh   # 梯子のみ（入力は既存の crunner ログから）
```

比較元）、`395c_ctx_holder.cu`、`rev386_validation_helpers.py`。入力はディスパッチャの
`src=` から読み、サイズ（56,707,896 B）でゲートする。

### 402への接続

- P2成立・P3反証 → 本番は133,56xで確定、`NQ_EXTRA_CTX` は不活性。402は104バイト
  詰め替えへ（P4〜P6が表明どおりなら）。掃引はホルダー方式で。
- P3成立 → 402の前に、`-g` にホルダーを組み込む小リビジョン（r6型の交互A/B）で
  413 msを取り戻す価値がある。
- P5反証 → 詰め替えは保留。
