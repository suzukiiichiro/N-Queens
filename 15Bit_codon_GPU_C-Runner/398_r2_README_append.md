## 398-r2 — 測定を止めていた1つの下限を下げる

### 398が止まった箇所

W1アンカーは成立しました。`133,197.422`、基準133,185から **+0.009%**、
`extra_ctx=2`、`free_mb=21762`、MATCH。**397で確立したV4（ディスパッチャ
なしで本番状態を再現）が、実運用で確認できました。**

止まったのはその次です。mode-37のCRunnerディスパッチが `N>=21` で
ゲートされていました。

```python
if use_gpu and N>=21 and bench_mode==37:
```

したがって `-g 20 20` と `-g 19 19` はCodon側のGPU経路を通り、正しい答え
（39,029,188,884 / 4,968,057,848、ともに `ok`）は出しましたが、
**CRunnerログもスケジュール済み入力も作られませんでした。** プロファイル
する対象がない。

入力生成4段のうち前半2段（constellation stream、soa_ref dump）は
**Codonバイナリの内側**にあるため、外部スクリプトだけでは作れません。

### r2が変えるもの — 実行行1つ

`CRUNNER_MIN_N:int=19` を新設し、**mode-37のゲートだけ**をこれに置き換え
ます。他の9つの `N>=21` ゲート（mode 30/31、32、33、34、35、36、38、39、
および末尾のガード）は**触りません**。ハーネスがその9つが残っていることを
静的に数えます。

安全性は自己検査です。N=19/20 の `required_maxd` は14以下なので
`crunner_select_entry_index()` は同じ表の行に解決し、CRunnerは
**Codon経路が既に `ok` を出したのと同じオラクル表**と突き合わせます。
万一 `required_maxd>14` なら `entry_idx<0` で `maxd-unsupported` を出して
break する既存経路に乗ります。

Py差分は**実行行 removed=4 added=5**（`VERSION_TAG`、`REV_TAG`、テーブル、
mode-37のゲート、＋定数1行）。`.cu` は398のリネームで、コード領域全体
`c5dbde3f1002229b…`、カーネル領域は395a r2の `ebd7f523deb59134…` のままです。

### 新たに認識したリスク — W6が生命線である理由

N=21 の `k_per_thread` は **79.1**。N=20 はレコード数がおよそ1/8になるので
`k_per_thread` は **10前後**に落ちます。**スレッド間の負荷平均化はN=21より
弱い。**

したがって「N=20がN=21の代表である」ことは**仮定してはなりません**。
N=21では Occupancy と Scheduler Statistics を396で実測済みなので、
**W6でそれと直接突き合わせます**。これは形式的な確認ではなく、本リビジョン
の結論が使えるかどうかを決める検証です。

### 事前登録予測（実測前に固定）

1. **W1**: アンカーが 133,185 の ±0.15%。398で成立済み（+0.009%）。
2. **W2**: `-g 20 20` と `-g 19 19` が**CRunner経路を通り**、crunnerログに
   `[gpu-run-done]` が出る。**398で落ちたのはここ。**
3. **W3**: N=20 の支配的warpストール理由は**分岐解決系で25%以上**。
   反証されれば律速要因は移動しており、399は最適化ファミリを変える。
4. **W4**: ローカルメモリの sectors/request。
   **表明する予測: ≥ 2、すなわち(b)発散が支配的。**
   ≤ 1.2 なら(b)は棄却され、量が効いている。**そのときに限り**98ビットを
   96に収める工夫に価値が出ます。
5. **W5**: N=19 と N=20 でストール理由の上位3件の順序が一致する。
   一致すればN=21の答えとして採用。しなければ順位はN依存。
6. **W6**: N=20 の達成オカパンシーが **10.32% ±3ポイント**、No Eligible が
   **61.63% ±5ポイント**以内。**外れたらN=20は代理として使えず、N=21を
   夜間に回す判断になります。**
