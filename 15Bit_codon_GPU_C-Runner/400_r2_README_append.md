## 400-r2 — 測る中身は同じ。規模を1段下げる

400は掃引をN=20、確認をN=21で行う設計で通しで約45分でした。**新しいハーネスの
デバッグには長すぎます。** r2は全部を1段下げます。

| | 400 | **400-r2** | 1実行 |
|---|---|---|---:|
| 掃引 | N=20 | **N=19** | 2,121.6 ms |
| 確認 | N=21 | **N=20** | 16,413.9 ms |
| 任意 | N=22 | **N=21** | 133,197.4 ms |

```
掃引 10構成 × 3反復 = 1.1分
確認  2構成 × 3反復 = 1.6分
```

ビルドと入力生成、ncuを含めて**通しで約15分**です。1行で本番規模に戻せます。

```
NPROF=20 NCONF=21 NBIG=22 bash 400_r2_validate.sh
```

`.cu` は400のリネーム（コード領域全体 `6821abd1af74405b…` が一致、カーネル領域は
`ebd7f523…`）、Pyは実行行3行の差分。**測る中身は1つも変えていません。**

### 小規模化が持ち込む偏り — 明記します

スレッドあたりレコード数 `k` はNとともに落ちます。

| stride | N=19 | N=20 | N=21 |
|---:|---:|---:|---:|
| 25,600 | 35.0 | 53.5 | 79.1 |
| 81,920 | 11.0 | 16.7 | 24.7 |
| 122,880 | 7.3 | 11.1 | 16.5 |
| 163,840 | **5.5** | 8.4 | 12.4 |

`k` が小さいほど394fの均衡が効きません。つまり**デバッグ規模は、掃引が探している
大stride構成に対して不利に働きます。**

> **N=19での空振りは仮説の反証になりません。** 判断はN=20の確認セルで下します。

ハーネスもそのように振る舞います。N=19で1%を超えなかった場合、`Z3_REFUTED` では
なく **`Z3_not_reached_at_debug_scale`** を出し、その旨を明記して先へ進みます。
**棄却の判定はN=20の結果で行い**、そこで1%を超えなければ `Z3_REFUTED_at_N20` を
出します。

### 変更点（400からの差分）

- `NPROF` / `NCONF` / `NBIG` の3変数化。既定 19 / 20 / 21
- オラクルはN=18〜23の表から自動引き。ハードコードを廃止
- 確認Nの入力も**ディスパッチャで生成し、`src=` から読み取る**（`IN21` の
  ハードコードを廃止）。N=20の入力が無い環境でも動きます
- **Z3の最終判定を確認Nへ移動**（上記の偏りへの対処）
- `WITH_N22` → `WITH_NBIG`（旧名も受け付けます）

### 事前登録（400のZ1〜Z6をNだけずらして継承）

1. **Z1**: カーネル領域sha `ebd7f523`、ptxas 37レジスタ/208Bフレーム、
   `NQ_BLOCK` 未設定で `BLOCK=32`（ディスパッチャ実行のログで確認）。
2. **Z2**: stride 25,600固定の梱包対照は ±2%以内。
3. **Z3**: **32 warps/SM 以上の構成の少なくとも1つが5%以上速い。**
   N=19では上記の偏りにより即棄却とせず、**N=20の確認で判断**。
4. **Z4**: 勝者で Achieved Occupancy と Active Warps Per Scheduler が上がり、
   `wait` のストール占有率が下がる。
5. **Z5**: 勝者はN=20へ、N=19での相対利得の半分以上を持ち越す。
6. **Z6（`WITH_NBIG=1`）**: 勝者はN=21でもベースラインを上回る。

```
STATIC_ONLY=1 bash 400_r2_validate.sh   # OK=16
              bash 400_r2_validate.sh   # 約15分
WITH_NBIG=1   bash 400_r2_validate.sh   # + N=21確認（さらに約15分）
NPROF=20 NCONF=21 NBIG=22 bash 400_r2_validate.sh   # 本番規模
```
