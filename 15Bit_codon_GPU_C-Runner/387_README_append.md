## 387: `-g`単独での連続N出力

**位置づけ**: 一番最初(今週月曜)にご依頼いただいた項目1
「起動は-gのみのオプションでN5からN22(以降)を連続的に出力」への対応。
385(CRunnerディスパッチ)・386/386a/386b(整理)を経て、ようやく土台が
揃ったので実装した。

**変更点(3箇所、すべて`main()`の外側の定数2つ+ディスパッチ内の
制御フロー1箇所)**:

1. `A10G_FINAL_DEFAULT_BENCH_MODE`を`31`(旧241からのsplit145既定)から
   `37`(385/386のCRunner os.systemディスパッチ)へ変更。bare `-g`は
   これでN=21以降、385/386で実機確認済みの経路(Cバイナリへの
   シェルアウト)を自動的に使う。`kernel_ms`は変わらず約201,232ms
   (386a/386bのsplit145実行が約5分かかっていたのに対し、CRunner経路は
   約3分23秒)。
2. `DEFAULT_RANGE_NMAX_EXCLUSIVE`を`24`から`28`へ拡大。**この28は
   恣意的な数字ではなく、`expected[]`オラクル表(index 0〜27、28要素)と
   `select_dynamic_preset_queens`が定義しているN範囲の実際の上限**。
   これを超えて拡大すると`expected[N]`が範囲外アクセスになる。
3. `bench_mode==37`の2つの失敗経路(`[crunner-unsupported]`・
   `[crunner-input-missing]`)を、`continue`から`break`に変更。
   `required_maxd`はNに対して単調非減少という観察(366/368)に基づき、
   一度未対応になれば以降のNも大半は未対応なので、`continue`のまま
   だと同じメッセージを繰り返すだけになる。`break`で「行けるところ
   まで進めて止まる」という当初のご依頼通りの挙動にした。

**触れていないもの**: `bench_mode==31`(split145)自体は無変更で、
明示的に`31`を指定すれば引き続き使える。N=6〜20はどのbench_mode専用
分岐にも該当せず、元の`exec_solutions()`経路をそのまま通るため、今回の
変更の影響を受けない。

**重要な注意点(実行前にお伝えしたいこと)**: N=22の`bench_mode=37`
経路には、`constellations_N22_7.bin.soa_ref_361.bin.maxd14only_363.bin`
(N=22はpreset_queens=7)というmaxd14絞り込み済みファイルが必要です。
過去のN=22検証は`bench_mode=33`(Codon内蔵のsingle-shot、生のstream
binを直接読む方式)で行われていたはずなので、**このファイルがまだ
存在しない可能性があります**。もし無ければ、bare `-g`はN=22で
`[crunner-input-missing]`として**クリーンに停止**します。これは
385で意図的に選んだ設計(外部フィルタスクリプトの自動実行はしない)
通りの挙動であり、不具合ではありません。N=21で止まってもN=22まで
進んでも、どちらも正常な結果として扱ってください。

**事前予測**: bare `-g`はN=5〜20を高速に処理し(元々の`exec_solutions()`
経路、無変更)、N=21で`total=314666222712`・`ok`(約3分23秒)を表示、
N=22はファイルの有無次第で`total=2691008701644`・`ok`か
`[crunner-input-missing]`のいずれかで**クラッシュせず**停止する、と
予測する。

**結果**: (鈴木さんの実機実行後、ここに追記。`387_validate.sh`は
N=21が確実にオラクル一致することと、N=22が「オラクル一致」または
「クリーンな停止」のどちらかであること──クラッシュや無限ループで
ないこと──を確認する。かなり時間のかかるテストです、N=21だけで
約3〜4分見込みです)
