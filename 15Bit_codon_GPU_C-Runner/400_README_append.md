## 400 — BLOCK=32が押さえていたオカパンシーの天井を外す

### 399-r2でU5がついに答えられた

N=20、`selected`（発行であってストールではない）を除いた実ストール。

| 理由 | 割合 | cycles/issue |
|---|---:|---:|
| **wait** | **45.05%** | 2.32 |
| branch_resolving | 26.80% | 1.38 |
| long_scoreboard | 13.98% | 0.72 |
| no_instruction | 7.57% | 0.39 |

**N=19も同順位**。代理の人工物ではありません。

首位の `wait` は**固定レイテンシ依存待ち**です。**メモリ起因は14%にすぎません。**
これは398-r2のSpeedOfLight（L1/TEX 70.64%）から私が述べた「L1律速」を**覆します**。
L1パイプは忙しいが、ワープはそこで止まっていない。スケジューラあたり
**2.43／12ワープ**しか居らず、短いレイテンシすら隠せていない。

なお399-r2は並び順の軸も閉じました。順序は35.2%の価値を持ちますが、394fが
既にそれを取り切っており、**実測コストソートですら勝てません**（+1.96%、+2.81%）。
レーン稼働率も値札を付けられませんでした（局所傾きと大域傾きが6倍違う）。

### 持ち上げられたことのない天井

sm_86 はSMあたり最大 **16ブロック・48ワープ**。BLOCK=32 では1ブロック=1ワープ
なので、**グリッドをいくら大きくしても理論オカパンシーは 16/48 = 33.3% で頭打ち**。
しかも本番の 800ブロック ÷ 80SM = **10ブロック/SM** で、その16にすら届いていません。

`MAX_BLOCKS` は394b/394gで掃引済みですが、**`BLOCK` は一度も動かされていません。**
そしてレジスタは制約ではありません（37本で52ワープ分）。

```
BLOCK= 64 -> 16ブロック×2 = 32/48 = 66.7%
BLOCK=128 -> 12ブロック×4 = 48/48 = 100%
```

### 400が変えるもの — ホスト側の1ノブ

`NQ_BLOCK` を新設（32/64/128/256/512/1024、既定32）。BLOCKはカーネルには
`blockDim.x` と起動構成としてしか届かないので、**カーネル領域のsha256は
`ebd7f523…` のまま**です。ハーネスがゲートします。`.cu` のコード領域差分は
**removed=1 added=30**。

### 掃引の格子

| BLOCK | MAX_BLOCKS | stride | blocks/SM | warps/SM |
|---:|---:|---:|---:|---:|
| 32 | 800 | 25,600 | 10.0 | 10 ← 現行 |
| 64 | 400 | 25,600 | 5.0 | 10 |
| 128 | 200 | 25,600 | 2.5 | 8 |
| 32 | 1,280 | 40,960 | 16.0 | 16（BLOCK=32の天井） |
| 64 | 640 | 40,960 | 8.0 | 16 |
| 64 | 1,280 | 81,920 | 16.0 | 32 |
| 128 | 640 | 81,920 | 8.0 | 32 |
| **128** | **960** | 122,880 | 12.0 | **48（100%）** |
| 128 | 1,280 | 163,840 | 16.0 | 48 |
| 256 | 480 | 122,880 | 6.0 | 48 |

上3行が **stride固定の「梱包対照」**（warps/SMが同じなので、形だけの影響を分離）。
下7行が**常駐ワープを増やす本体**です。

N=20で1点16秒・3反復、ノイズフロアは399-r2実測で0.003〜0.05%。**極めて安い測定**です。

測定は `NQ_EXTRA_CTX=2` で行います。397のV4・398のW1で確立した、
**ディスパッチャなしで本番の3コンテキスト状態を再現する**方法です。

### 仮定しないこと

ワープを増やせば常駐ローカルメモリも増え、スレッドあたりレコード数が減って
394fの均衡が弱まります。**差引が正かどうかは論じずに測ります。** 全構成を同一
セッション・同一ベースラインで計測し、勝者はN=21で確認し、**オカパンシーが実際に
上がり `wait` が実際に下がったことをncuで確かめてから**信じます。

### 事前登録予測（実測前に固定）

1. **Z1**: カーネル領域sha `ebd7f523` のまま、ptxasのレジスタ37本・フレーム208B
   のまま、`NQ_BLOCK` 未設定で `BLOCK=32`（不活性、ディスパッチャ実行のログで確認）。
2. **Z2**: stride 25,600 固定のまま BLOCK だけ変える梱包対照は **±2%以内**。
3. **Z3（本命）**: **表明する予測——32 warps/SM 以上の構成のうち少なくとも1つが
   ベースラインより5%以上速い。**
   **1%を超えて勝つ構成が皆無なら、オカパンシーは梃子ではなく、`wait` の読み
   自体をやり直します。**
4. **Z4**: 勝者では Achieved Occupancy と Active Warps Per Scheduler が上がり、
   **`wait` のストール占有率が下がる**。結果だけでなく機構を確認します。
5. **Z5**: 勝者はN=21へ、N=20での相対利得の**半分以上**を持ち越す。
6. **Z6（`WITH_N22=1`）**: 勝者はN=22でもベースラインを上回る。

**全走行がオラクルゲート下です。** BLOCKやMAX_BLOCKSを変えても、同じレコードを
スレッドへ再分割するだけなので、答えは動いてはなりません。

### N=22について

**起動構成はNに依らない軸なので、効くならN=22にも効くはずです。**
395c-r6の413 ms（`free_mb` 21762の狭い切り欠き）はN=22に持ち越せませんが、
**この軸は持ち越せる見込みがあります**。`WITH_N22=1` で確認セルが走ります
（入力生成込みで長く、1構成あたり約19分なので各1反復・参考値扱い）。

```
STATIC_ONLY=1 bash 400_validate.sh   # OK=16
              bash 400_validate.sh   # 約45分
WITH_N22=1    bash 400_validate.sh   # + N=22確認（さらに1時間前後）
NCU_PREFIX=sudo bash 400_validate.sh
```

**ハーネス全体をsudoで走らせないでください。** ncu呼び出しのみ昇格します。
