## 399 — 宿題を片付け、レーン稼働率の軸を開く

### 398-r2が測ったもの（N=20 / N=19、それぞれ自前の394fスケジュール）

| | N=20 | N=19 | N=21（396実測） |
|---|---:|---:|---:|
| Avg. Active Threads Per Warp | **10.53 / 32** | 10.25 / 32 | — |
| sectors per local request | 4.690 / 4.691 | 4.588 | — |
| L1/TEX Throughput | **70.64%** | — | — |
| Compute (SM) Throughput | 31.55% | — | — |
| No Eligible | 60.53% | 59.76% | 61.63% |
| Active Warps Per Scheduler | 2.43 | — | 2.41 |

ローカルメモリの1アクセスに、2段の損失が掛かっています。

```
レーン稼働率   10.53 / 32                = 32.9%
セクタ効率     有効 84.2 B / 転送 150.1 B = 56.1%
実効効率                                  = 18.5%
```

カーネルは**L1律速**で、そのトラフィックはローカルメモリ上のDFSスタック。
16.4秒で 33.7 TB のセクタ転送（約2.05 TB/s）、1レコードあたり16.4万アクセス。

**397が立てた「(a)量 か (b)発散 か」は誤った二分法でした。** 両者は同じ壁の
別の顔です。フレームを縮めればセクタも比例して減り、生きレーンが増えれば
セクタあたりの無駄が減る。**397の着想は正しく、rdのマスクだけが無効でした。**

### 私の校正ミスの訂正

W4の閾値「sectors/request ≥ 2 なら発散」は**無意味でした**。スタックは
`uint64_t` なので、32レーンが同じ添字を触る完全合体アクセスでも
32×8 = 256 B = **8セクタ**です。1ではありません。

発散の証拠は `Avg. Active Threads Per Warp = 10.53/32` の方にありました。
こちらは曖昧さがなく、N=19（10.25）とも一致しています。

### なぜ順序が効きうるのか、そしてなぜ安全なのか

スレッド `tid` はレコード `tid, tid+stride, tid+2·stride, …` を取ります。
したがってステップ k においてワープ w の32レーンが持つのは
**`[k·stride + w·32 .. +31]`、スケジュール済みファイル上の連続32レコード**です。

> **どの32レコードが同じワープを共有するかは、ホスト側の並び順が完全に
> 決めています。** そして並び順は394fの出力です。

そして**並べ替えは構成上安全**です。レコードは独立した課題で、結果はその
総和なので、任意の置換は同じ `total_sum` を出さねばなりません。
それでも全走行にオラクルゲートを掛けます。

機構の仮説は**課題長の発散**です。各スレッドは `process_one_task()` を最後まで
走らせてから次のレコードへ進むので、ワープのループは最も長いレーンに律速され、
残りは遊びます。似た長さの課題を同じワープに集められれば、レーン稼働率は上がる。

### 事前登録予測（実測前に固定）

1. **X1**: ストール理由の首位は **long_scoreboard 系（メモリ待ち）で25%以上**。
   **394a時点の「分岐解決が支配的」という知見を、私は覆す側に賭けます。**
   根拠はL1が70.64%で最大パイプ、発行あたり6.14 warp-cycle、
   1レコード16.4万回のローカルアクセス。
   **分岐解決が首位なら、レーン稼働率の解釈もやり直しです。**
2. **X2**: 連続32レコード組の内部分散 ÷ 全体分散 **≥ 0.8**。すなわち394fは
   似たレコードを同じワープに集めていない。**≤ 0.3 なら既に集まっており、
   この軸の余地は小さい。GPU不要で判ります。**
3. **X3（対照）**: 無作為シャッフルは394f順より **2%以上遅い**。
   **差が0.5%以内なら並び順は無関係**で、フェーズCの軸そのものが死にます。
   これは価値ある否定的結果で、無駄な労力を大きく節約します。
4. **X4**: **表明する予測——proxyソートはどれもC0（394f）を1%超えて上回らない。**
   394fはまさにこの問題のために設計されています。このフェーズの価値は
   X3の対照と、フェーズDのレーン稼働率実測にあり、勝つことではありません。
5. **X5**: `kernel_ms` が1%以上動いた順序では `Avg Active Threads Per Warp` も
   同じ向きに動く。機構と指標が結びついていることの確認。

### 置換不変性はハードゲート

全順序で `total_sum = 39,029,188,884`（N=20）を要求します。**成り立たなければ
レコード間に隠れた依存があるということで、並べ替え実験以前に本案件の前提が
崩れます。** ハーネスはそこで停止し、時間を報告しません。

置換ツールは手元で自己検査済みです（4種すべてでバイト多重集合が一致）。
