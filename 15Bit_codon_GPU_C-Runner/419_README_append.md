## 417-r3 run3 の結果（2026-11-04 01:34 完走）— **N=25 の総和がオラクルと不一致、417 の設計ミス**

run3（10/26 15:20 起動、`-g 25 25`）は rc=0 で完走したが、**total_sum 2,204,354,806,741,818 ≠ 2,207,893,435,808,352**（−3,538,629,066,534、−0.16%）。kernel_ms 727,937,344（202.2 h、norm 727,469,080、sm_mean 1708.9、67 ℃）、results.bin sha `3ffe8998`（**誤った基準なので使わない**）。run1（10/14、`-g 5 25`）は N=21〜24 を再現（N=24 +0.30%）し N=25 を 200.6 h で、run2（10/24）は 43.8 h で、ともに EC2 ホスト劣化（退役通知）により喪失。N=25 の単発所要は約 202 h で確定。

### 原因：深さごとのスケジュール語の桁あふれ

`process_one_task` は深さごとのニブル（block code 3 ビット＋future-check 1 ビット）を `schedule_lo/schedule_hi` の **64 ビット＝16 スロット（深さ 0〜15）**に詰める。`.py` の `packed_schedule_words_for_maxd` の注釈は「16 slots, depths 0..15」、`.cu` の注釈は「schedule_depth ≤ 14」。`required_maxd` は終端アクションが出る深さなので、N=24 の 16 は深さ 0〜15 で丁度一杯、**N=25 の 17（フィルタのヒストグラム `17:98138478`＝全件）は深さ 16 のニブルの置き場が無い**：`frame_nibble << 32` と `schedule64 >> 64` はともに未定義シフト。417 は祖先フレームを 16 段に延ばしたが、スケジュール語を延ばしていない（カーネル名 `maxd16` の由来）。深さ 16＝終端深さで、そこに mark 行（block code ≠ 0）が重なるレコードだけ nld/nrd の段差（2・3）が 1 として計算され、数え漏れる。

Y2e（417 ＝ `417_ref_dfs`、等間隔 1,024 件）が見なかった理由は二つ。(1) **参照が同じ 64 ビット詰めを写していた**（x86 はシフト量をマスクするので、両者が同じ誤りで一致）。参照は検査対象と表現を共有してはならない、と自分でヘッダに書きながら、スケジュール前計算を「共有部分」に入れていた。(2) Y2 は CPU 対 CPU だけで、GPU 対 CPU の実データ等価を見ていなかった。

### 恒久ルール案

- **39**：新しい N に進むときは、フレーム数だけでなく**深さに比例する全ての語**（スケジュール語、マスク）の容量を `required_maxd` と突き合わせる。CPU ハーネスは容量超過で abort する（419 で実装）。
- **40**：独立参照は、検査対象と**データ表現を共有しない**（配列で持つ、詰めない）。
- **41**：Y2 に GPU 対 CPU の実データ等価を 1 セル入れる（1 件/スレッドのスライスなら results.bin が件ごとの値になる）。

## 419 — N=25 の修正（配置 425 のスケジュール語を 3 ビット×21 深さに）、N≤24 は SASS 不変

### 修正（`419_kernel_maxd16.cu`、配置 425 の実体だけ）

- fc フラグは `future_check_mask` に既にある（404-r3 でループはマスクを読む）ので、語には **3 ビットの block code だけ**を、同じ `schedule_hi:lo` の 64 ビットに `code << (depth×3)` で詰める：21 深さ（N=25 は 17、N=26 は 18）。深さ 10 の 3 ビットは 2 語にまたがる。
- 取り出し `(schedule64 >> (cur_depth×3)) & 7`。×4 のシフト量計算が ×3 の IMAD になるだけで、ループ命令数は 111±1 の見込み。
- root 高速路は深さ 0 の fc をマスクから取る（`future_check_mask & 1`、404-r3 が読む同じビット）。
- CPU ハーネスに `[SCHEDULE-WORD-OVERFLOW]` の abort（4 ビット配置は深さ >15、425 は >20）。
- 非 425 の文は原文のまま（425 の詰め込みは `if constexpr` の枝、取り出しと root の 2 箇所は実体ごとに畳まれる定数条件式）。417 比 code-region removed=5 added=25、kernel sha `3b67e26c`。PACK 定数不変。SASS 同一をハードで要求。
- **r1（11/4 21:38）は S2 で撤回**：`if constexpr` のブロックと新変数 `schedule_bc` で書いたところ、<402> の SASS が命令数・ループ長は同じ（446／109）まま並び替わった（sha 109788c8）。403-r2 で学んだ「死んだ枝・余分な変数が PTX の順序を変える」の再現。

`419_ref_dfs.c`：block code を **配列で持つ**（詰めない、深さ 31 まで）。`419_sched_scan.c`：入力全件のスケジュールを走査し、ヒストグラム・runaway・深さ 16 以降の block code ≠ 0 の件数（影響クラス A）を出し、影響クラスの等間隔抽出（スライス T）と等間隔サンプルを書く。

`419Py_kernel_maxd16_final.py`：実行行 3 行（VERSION_TAG、REV_TAG、`CRunnerEntry(17, ./419_kernel_maxd16)`）＋419 ノート。
