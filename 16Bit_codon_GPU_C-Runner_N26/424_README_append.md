## 424 現行の探索のまま「待たせない」（レーン補充、`NQ_LOGIC=refill`）（2026-11-19 納品、実機未実行）

### 1. 423 から分かったこと（経緯）

- 423（動的な行選択、`NQ_LOGIC=mrv`）は正しさを全通過したが、スライス B で 419 比 0.9407。事前登録（0.40〜0.65、反証 0.90 以上）に対して反証 → 不採用（`423_results_README_append.md`）。
- SASS の行ループは 1 行 19 命令で見積もりどおり。電力は 299 W → 152 W。**仕事は半分になったが、同時に働くレーンも半分になった。**
- suzuki の判断（11/19）：最適化は続ける。まず CPU 上のワープ模擬で見込みを確かめてから GPU に載せる。

### 2. ワープ模擬（`423_warp_sim.c`）

今日ビルドしたバイナリの SASS から区間ごとの命令数を読み取り、32 レーンを同時に進めて「ワープが費やす命令スロット」を数える。レーンが持つレコードは実際の並び（スレッド tid は tid、tid+stride、…）のとおり。

| 模擬が実測を再現できるか | 模擬 | 実測 |
|---|---|---|
| 現行 `<425>` のレーン稼働率 | 34.8% | 32.9%（N=20、ncu、398-r2） |
| 入れ子の mrv（423）÷ 現行 | 0.951 | 0.941（DM960 ÷ D960） |

レーンが遊ぶ原因は 2 つ。

- **(a) レコード終わりの待ち**：レコードを終えたレーンは、同じワープの一番長いレコードが終わるまで待つ。SASS では探索ループが合流点の対（`<425>`：`BSSY B4` 0x1390 〜 `BSYNC B4` 0x1aa0）の内側にある。398-r2 のノートの「課題長の発散」。
- **(b) 反復の中の待ち**：レーンごとに通る経路が違うぶん（即死・future check・降下・pop）。

(a) は探索を変えずに消せる。これが 424。

### 3. 模擬の結果（現行そのまま = 1.000）

| データ（N=25） | 案 | 模擬したラウンド数での値 | 極限 |
|---|---|---|---|
| スライス T、2 ワープ × 4 ラウンド（256 件） | 現行（そのまま） | 1.000（稼働率 34.8%） | — |
| 〃 | 入れ子の mrv（423） | 0.951 | — |
| 〃 | **現行 ＋ 補充（424）** | **0.867** | **0.69** |
| 〃 | 平らな mrv ＋ 補充（1 反復 4 行） | 0.747 | 0.60 |
| スライス B、2 ワープ × 2 ラウンド（128 件） | 現行（そのまま） | 1.000（稼働率 33.1%） | — |
| 〃 | **現行 ＋ 補充（424）** | **0.962** | **0.64** |

- スライス B は 2 ラウンドしか模擬していない（1 件が重く、CPU 時間の都合）。2 ラウンドでは 4% しか出ないが、これは各レーンの持ち分が 2 件しかなく、合計が一番多いレーンに律速されるため。
- ラウンドごとの「最長 ÷ 平均」は T でも B でも 1.4〜1.65。補充すると、律速は「レーンごとの合計の最長 ÷ 平均」に変わり、これはレコード数の平方根に反比例して 1 に近づく（B の 2 ラウンドで 1.51、4 ラウンドの T で 1.28）。
- この縮み方をスライス B の実機セル（10 件/スレッド）に当てはめると 約 0.78。

- 「極限」は、全レーンが最後までレコードを持ち続ける場合（1 スレッドあたりのレコードが多い本番走行に近い）。ラウンド数が少ないと、各レーンの最後のレコードが終わったあとの遊びが残る。
- 平らな mrv の区間長は見積もりで、未コンパイル。424 が通ったあとの 2 段目の候補。
- 模擬が数えるのは命令の個数だけ。ローカルメモリの待ち、クロック、電力上限は入っていない。**現行は 299 W の電力上限に当たっているので、稼働レーンが増えるとクロックが下がって利得が削られる可能性がある**（norm_ms と電力の記録で見る）。

### 4. 424 の中身

`NQ_LOGIC=refill` で `process_stream_refill`／`kernel_refill_gpu` が走る。

| | 現行（419） | 424（`NQ_LOGIC=refill`） |
|---|---|---|
| 1 ステップ・pop | 配置 425 の文 | **同じ文**（同じ LOP3 形） |
| フレーム、スケジュール語 | 12 B × 16、3 bit × 21 | 同じ |
| スタックが空になったら | 探索ループを抜ける → ワープ全員を待つ → 次のレコード | **その場で次のレコード（idx + stride）を読み、スケジュールをたどって続ける** |
| ループを抜けるのは | レコードごと | スレッドのレコードが尽きたときの 1 回 |
| 根の高速経路（根の候補が 1〜2 個） | あり | なし（一般のステップが深さ 0 で同じ仕事をする） |
| 対応する N | 21〜25（配置 402〜425） | 25 以下（配置 425 のみ） |

- スレッド別の和は 419 と同じなので、**results.bin は同じ stride でバイト一致するはず**。
- 未設定（`NQ_LOGIC` なし）は 419 そのまま（kernel 領域 sha `3b67e26c`、419 比 removed=3 added=729）。`NQ_LOGIC=mrv` は 423 のまま残してある。
- N=25 のスライス B・C・T（計 309,248 件）に「根の候補が 2 個以下」のレコードは 0 件。N=21・22 では GPU セルのバイト一致がこの経路を確かめる。

### 5. 手元で確認したこと（GPU なし）

| 確認 | 結果 |
|---|---|
| CPU 等価、スライス T 全 1,024 件を stride 32（32 スレッド × 32 件を続けて処理） | スレッド別の和 = 参照（`419_ref_dfs`）の和、総和 1,498,221,984 |
| CPU 等価、スライス T 先頭 64 件を 1 件/スレッド | 1 件ごとの値 = 参照 |
| CPU 等価、スライス C 先頭 256 件を 1 件/スレッド | 1 件ごとの値 = 参照、総和 4,054,142,744 |
| 静的 | kernel 領域 sha `3b67e26c`（= 419）、.cu 419 比 3/729、.py 419Py 比 3/3 |
| CUDA C++ としての構文 | clang の CUDA フロントエンドでファイル全体が通過 |
| ptxas（clang 経由、目安） | refill：フレーム 192 B、spill 0、レジスタ 47。既存 5 実体と mrv は 423 のときと同じ |
| ハーネス | 偽のツール（ランナーは CPU ハーネスで代用、6 件スライス）で静的 → ビルド → Y2 → 全セル → tar まで通した |

スライス C の残り 768 件と T の 1 件ごとの照合は手元では省いた（NQ_CRunner の Y2c／Y2t が全 1,024 件を sha で照合する。参照の sha は 11/19 に手元で計算し、423 の走行が NQ_CRunner 上で同じ総和を再現している）。

### 6. 確かでない点

- **nvcc が 1 本のループとして出すかは未確認。** 探索ループを囲む合流点が残れば待ちは消えない。ハーネスの S8 が、SASS 中の「スタックのロードを含むループ」の数と長さを 419 と並べて出す（419 は 2 つ、424 は 1 つのはず）。
- **待ちの仕組みは SASS の読みと模擬による推定。** 決め手は GPU の実測。
- **N=21・N=22 は模擬していない**（入力が手元にない）。予測の幅を広く置いた。
- **レジスタが増える**（clang 経由で 47、`<425>` は 37）。レコードごとの定数だったもの（スケジュール語、マスク）がループをまたぐ変数になったため。主ループの命令数が増える可能性がある（S8 の innermost loop と `<425>` の 111 を比べる）。

### 7. 実行手順（NQ_CRunner、GPU が空いていること）

置くファイル：`424_kernel_maxd16.cu`、`424Py_kernel_maxd16_final.py`、`424_validate.sh`（＋この追記）。

```bash
STATIC_ONLY=1 bash 424_validate.sh        # 1 分。必要な入力をすべて探して、見つけた場所を表示する
screen -S nq424
bash 424_validate.sh 2>&1 | tee 424_validate_stdout.log
```

- 423 で 3 回止まった反省から、**必要な入力は最初の静的段ですべて探す**（まず実行ディレクトリ、無ければ `$HOME` 以下を `find`）。見つからない必須ファイルがあれば、GPU を使う前に止まる。探す場所は `SEARCH_ROOT=<ディレクトリ>` で変えられる。
- 所要：静的＋ビルド 3 分、CPU 等価 約 20 分、N=21 の 3 セル 6 分、N=22 の 2 セル 約 25 分（入力があれば。`SKIP_N22=1` で省略）、DR960 52 分以下。
- 送っていただきたいもの：`424_validate_stdout.log` と `424_validate_<日時>.tar.gz`。

| ゲート／セル | 内容 | 種別 |
|---|---|---|
| S0 | 静的、入力の所在、スライス 3 本の sha | ハード |
| S1 | ptxas：5 実体は 419 どおり、mrv ≦ 128 B、refill ≦ 200 B、spill 0 | ハード |
| S2〜S6 | 5 実体の SASS = 419 バイナリ | ハード（本番経路） |

| Y2c／Y2t | CPU：refill の 1 件ごとの値 = 参照（スライス C・T 各 1,024 件、sha で照合） | ハード |
| Y2s | CPU：スライス T を stride 32（32 件/スレッド）で、スレッド別の和 = 参照の和 | ハード |
| Y2d／Y3 | 既定経路 = 参照（64 件）、N=26 と `NQ_LOGIC=bad` は rc=3 | ハード |

### 8. 事前登録（実行前に固定）

比はすべて「refill ÷ そのまま」（クロックで正規化できるときは norm 値）。

| | セル | 予測 | 根拠 |
|---|---|---|---|
| **P1** | DR960 ÷ 419 の D960（3,099,327 ms） | **0.70〜0.90** | スライス B の模擬（2 ラウンド 0.962、縮み方から 10 件/スレッドで約 0.78） |
| P2 | R21 ÷ Z21（N=21、66 件/スレッド） | 0.62〜0.88 | 模擬なし。N=25 の「最長 ÷ 平均 ≒ 1.6」が N=21 でも同程度と仮定 |
| P3 | R22 ÷ Z22（N=22、約 930 件/スレッド） | 0.60〜0.85 | 同上。本番走行にいちばん近い |

- **反証**：P1 が 0.97 以上。そのときは S8（nvcc が 1 本のループにしたか）と電力の記録を読む。
- **採用則**：ハード全通過、P1 が 0.95 以下、かつ R21 が Z21 より遅くない → 425 で `-g` 経路（まず N=25）を refill に載せる（オラクルで確認）。届かなければ記録して閉じる。
- 幅が広いのは、(1) N=21・22 を模擬していない、(2) 電力上限とクロックの影響を模擬が見ていない、(3) グリッド全体の尾（ワープごとに終わる時刻が違う）を模擬が見ていない、の 3 点による。

### 9. 本番への影響

本番は 419 のまま。424 の走行は本番値を動かさない。採用になった場合、425 で `-g` 経路を refill に切り替える（まず N=25。N=21〜24 は配置 403〜424 の方が配置 425 より速いので、refill をそれらの配置に広げるかは 424 の N=21・22 の結果で決める）。
