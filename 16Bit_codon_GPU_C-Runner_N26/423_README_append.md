### 3. 423 の中身

**同じバイナリに 2 つ目の探索を足した。** `NQ_LOGIC=mrv` を付けると `process_one_task_mrv`／`kernel_mrv_gpu` が走る。付けなければ 419 そのまま（`process_one_task`・テンプレートカーネル・`select_pack_layout` は無変更、kernel 領域 sha `3b67e26c` のまま）。

| | 現行（419、`<425>`） | 423（`NQ_LOGIC=mrv`） |
|---|---|---|
| 行の順番 | スケジュールどおり（固定） | 毎回、候補が最少の行 |
| 枝刈り | 次の行の候補が空（＋1 行先の future check） | どの行かの候補が空／どの行にも置けない空き列がある／2 つの列が同じ行を要求 |
| 状態 | ld・rd・col・avail（段ごとに 12 B を保存） | 空き列 32 bit＋対角 2 本（各 64 bit、絶対座標）＋残り行 32 bit。保存しない |
| 行の候補 | 段を降りるたびに 1 行ぶん作る | `rw & fcol & ~(lo32(dA >> pos) \| hi32(dB << pos))` で必要なたびに作り直す |
| フレーム | 12 B × 16 段 = 192 B | 2 B（行・列番号・「兄弟なし」・pos）× 18 = 36 B |
| レコードごとの前処理 | スケジュール語 | 同じスケジュールをたどって行ごとの静的マスク 18 語（72 B） |
| ローカル合計 | 192 B | 108 B（Claude 側の ptxas で 112 B フレーム） |

- ノード 1 つ = 残り行を 1 巡（候補・和集合・2 回以上出た列・最少行を同時に取る）。強制行があるときだけ 2 巡目。
- 子は仮の状態（レジスタ）で評価し、生き残ったときだけフレームを積む。死ぬ子はローカルへの書き込みゼロ。
- pop は置いたクイーンの 4 ビットを消すだけ。その行の残り候補は、復元した状態から作り直して「最後に取った列より上」で切る（425 と同じ考え方）。
- 入力は現行の 28 B レコードのまま。sched ファイル、スライス、`-g` の入力構築は一切変わらない。

**11/18 の設計案から変えた点**（6 件の仕事量カウンタで決めた。結果は全変種で一致）：

| 変種 | 行の評価 | 強制行の走査 | 子 | 確定（push） |
|---|---|---|---|---|
| **既定（切替なし・強制あり）** | **15.11 億** | 0.99 億 | **2.86 億** | 2.16 億 |
| 強制なし（`MRV_FORCED=0`） | 18.08 億 | 0 | 3.46 億 | 2.45 億 |
| 残り 4 行以下で切替（`MRV_SWITCH=4`） | 15.03 億 | 0.92 億 | 3.28 億 | 2.44 億 |
| 残り 3 行以下で切替 | 15.07 億 | 0.97 億 | 2.96 億 | 2.23 億 |

- 「残り 4 行以下は現行方式に切替」は**入れなかった**。子を仮評価する形にすると、切替えても行の評価回数は減らず、子が 15% 増える。コンパイル時定数 `MRV_SWITCH`（既定 0）として残してある。
- 強制行は入れた（行の評価 −16%、子 −18%）。

### 4. 数え方が現行と同じである根拠

423 は葉（残り 1 行）で popcount(候補) を足す。現行 DFS は「最後の行に候補が 1 つ以上あれば 1」を足す。両者は **「そのレコードの行が使える列の種類 ≦ 行数」** なら一致する（最後の行に候補が 2 つ残ることがない）。

- `423_rows_scan.c` が入力全件でこの条件を検査する（ハーネスの SCAN、ハード）。
- 手元ではスライス C・T の 2,048 件すべてで 行数 18、列被覆 = 行数 = 空き列数、pos の最大 19。
- CPU ハーネスは条件を破るレコードで `[MRV-COVER-EXCEEDS-ROWS]` を出して abort する。

### 6. 分かっていないこと（正直な見積もり）

- **GPU での速度は未知。** nvcc ではまだ一度もビルドしていない。
- 机上の仕事量：6 件で「行の評価 15.1 億＋強制 1.0 億＋子 2.86 億」対 現行 14.3 億ステップ。行 1 回 約 18〜20 命令、現行 1 ステップ 約 55 命令（`<425>` の経路別命令数の加重平均）と置くと **約 0.5**。
- **CPU では、この GPU 向けの形は速くない。** 6 件・1 スレッドの CPU 時間は、参照 DFS（`419_ref_dfs`）14.5 s、プローブの規則 15 が 11.5 s（0.79 倍）に対し、423 の形は **14.1 s（0.97 倍、`-mpopcnt` あり）／20.0 s（1.38 倍、なし）**。スライス C 全体でも参照の約 0.9 倍。行の候補を毎回 64 bit シフト 2 回で作り直すぶん行 1 回あたりが重く、規則 15（段ごとに候補配列を持つ）の利得は CPU では出ていない。段ごとの配列を捨てたのは L1 に収めるためで、その代償がこれ。 GPU で利得が出るかどうかは「現行カーネルは明示スタックとフレーム詰めのぶん 1 ステップが CPU の約 2 倍重い」ことに掛かっている。ここが外れれば比は 0.65 を上に抜ける。
- レーン稼働率（現行 33%）と分岐の形がどう出るかは測るまで分からない。行ループの回数はレーンごとに違う（残り行数が違う）ので、ここは悪化する可能性がある。
- フレームが 192 B → 約 112 B になるので、960（12 warp/SM）が最適とは限らない。1280（16 warp/SM、BLOCK=32 での上限）で 57 KB、L1 の内側。M1280 セルで 1 点だけ測る。

### 8. 事前登録（実行前に固定、11/19 合意）

- **P1**：DM960 ÷ 419 の D960 が **0.40〜0.65**。**反証：0.90 以上。**
- **採用則**：ハード全通過 かつ 比が **0.50 以下（2 倍以上）** → 424 で `-g` 経路（N=21〜25）に載せる（各 N はオラクルで確認）。届かなければ記録して閉じる。本番は 419 のまま。
- 0.50〜0.90 に落ちた場合：採用則どおり「不採用」。ただし S7 の行ループ長と M1280 を見て、2 回目（423-r2）に値するかを suzuki が決める。

### 9. 本番への影響

- 本番は **419 のまま**（N=21 97,946／N=22 849,096／N=23 7,717,284／N=24 73,112,528／N=25 728,149,056 ms）。423 の走行は本番値を動かさない。
