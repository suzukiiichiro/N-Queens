### 3. 何が外れたか（SASS と電力から）

- **命令数の見積もりは当たっていた。** SASS の行ループ（`0x12d0`〜`0x13f0`）は 1 行あたり 19 命令（見積もり 18〜20）、強制行のループは 13 命令。mrv 全体は実命令 464（`<425>` は 454）。
- **外れたのはレーン稼働率。** 電力が 299 W → 152 W に半減している。クロックと使用率（100%）は同じなので、同時に動いているレーンが約半分になったと読める（電力からの推定で、直接の計測ではない）。
- 原因は制御の形。カーネルは「外側ループの中に、行ループ（回数は残り行数で 2〜17 回）、強制行ループ、葉、pop」が入れ子になっていて、SASS には分岐の合流点（BSSY／BSYNC）が 20 組ある。ワープ内の 32 レーンは別々のノードにいるので、内側ループの回数がそろわず、短く終わったレーンは長いレーンを待つ。
- つまり「1 スレッドあたりの仕事は約半分になったが、同時に働くレーンも約半分になった」。11/19 の机上モデルは命令数だけを数えており、この待ちを入れていなかった（Claude の見積もりの欠陥）。
- CPU では NQ_CRunner 上で参照 DFS の 0.85 倍（スライス C）／0.94 倍（T）。CPU には待ちが無いので、こちらが「仕事量」の実測に近い。プローブの規則 15（0.62 倍）との差は、行の候補を毎回作り直す費用。

### 4. 記録

- 423 は「動的な行選択を GPU に素直に移すと、仕事は半分になるがレーン稼働率も半分になる」という結果で閉じる。コードと `NQ_LOGIC=mrv` は 423 バイナリに残る（既定経路は 419 と同一 SASS）。
- 学び（恒久ルール案）：**探索の形を変えるリビジョンは、命令数だけでなく「ワープ単位の反復回数 × ループ本体の長さ」で見積もる。GPU に載せる前に、CPU 上で 32 レーンのワープを模擬して稼働率を出す。**
- 学び（ハーネス）：実行ディレクトリに無い入力（N=21 sched、N=25 sched、411 B1、419Py）で 3 回止まった。次のハーネスは最初の静的段で必要ファイルを全部確認し、無いものは `find` で探して候補を表示する。
